Amp 开发者 [Thorsten Ball](https://x.com/thorstenball/status/2114386050638336082) 总结了自己与编程 Agent 协作的 15 条建议。这里的 Agent，是能读取项目文件、运行命令，再根据结果继续调整代码的 AI 助手。

在这份[实战总结](https://x.com/i/article/2114385531811319808)里，Ball 把自己的精力放在两端：开始时交代需求和可检验的目标，结束时检查运行证据、把关影响全局的修改。中间的编写、运行和调整，让 Agent 自己连续做完，减少人逐轮传报错、给修改意见的陪跑。

**15 条建议总览**

（按原文顺序归纳；下方六个编号章节按主题展开讲解。）

1. **优先用最新、最强的模型**，把少出错、少返工的时间成本算进去。
2. **别先认定 Agent 的代码会变得不可维护**：它是否增加粗糙代码、这些代码是否难以维护，Ball 对这两点都不再确信。
3. **说清想要什么结果**，给 Agent 留出选择具体做法的空间。
4. **让整个研发流程对 Agent 可见**，从运行、日志到发布后的状态，都能取得实际反馈。
5. **把完成流程所需的工具接好**，例如工单、客户邮件、系统健康检查和功能开关。
6. **检验 Agent 是否真的用上团队知识**，用有、无规则和文档的对照来检查。
7. **减少本地环境的资源冲突**：作者更偏好远端机器，让 Agent 安装并运行所需工具。
8. **让 Agent 造工具来试验**，一次比较多个方案，或逐个验证可能原因。
9. **要求可以核对的完成证据**，例如完整走查、演示视频和改动前后的数字。
10. **给更完整的任务，异步等结果**，让 Agent 做完后等人判断，减少逐轮来回。
11. **用定时、唤醒和心跳继续跟进**，在指定时机查日志、确认上线或例行检查。
12. **一个任务留在一条会话里**，作者把早期对话的压缩整理交给工具，减少手动管理上下文。
13. **把会话留下来作为团队记忆**：在 Amp 中，顺着代码提交能追溯当时的讨论和决策。
14. **面向人的文字由自己来写**，作者只把排障步骤、事故报告和部分机械性文档交给 Agent。
15. **把人工代码审查集中在影响大的改动**，尤其是少数核心文件和数据库迁移。

#### 先选能减少返工的模型

Ball 倾向于使用最新、最强的模型，考虑的是可靠性与返工的时间成本。他举例假设：如果一个模型有 10% 的概率出错，因为事先不知道是哪 10%，人就不得不多次尝试并排查；为了便宜而选择能力稍弱的模型，可能会在反复试错中消耗更多工程师的时间。

#### 交代想要的结果，让它拿出证据

**把最终想要的结果说清楚，给 Agent 留出选择做法的空间。** Ball 举出的提示词例子很直接：

> “把字节码编译器和虚拟机做到你能达到的最快速度。提速不到 2 倍不要停。”

这里的两倍是任务目标。怎样判断它做到了？Ball 的另一条要求是：**拿出让人能核对的证据。**

如果缺少实际检验手段，Agent 很容易给出看似合理却缺乏支撑的文字答复。Ball 建议团队建立对证据的直觉，也可以在项目规范（如 `AGENTS.md`）中直接写明“哪些答复不算证据”。他看重的证据包括：

- 端到端走查：让任务从开始到最终结果实际走通
- 演示视频：直观展示程序运行时的实际表现
- 前后对比数字：在相同基准条件下展示改动前后的性能差异

只提目标、不规定具体做法，与严格验证结果之间形成了配合：人类不过度干预具体编写过程，而是通过端到端走通的运行结果与数据对比，来确认目标是否真正达成。

#### 让 Agent 自己运行、看报错、查日志

Agent 看不到外部系统的实际状态时，可能用听起来合理的猜测填补空白。比如它能写出一段优化代码，却未必知道程序运行后是否真的更快。

Ball 看重工具调用带来的实际反馈：代码运行失败时，Agent 能直接读到错误；查日志时，能核对系统到底发生了什么。他主张把从开发到上线、处理用户反馈的整条流程接进来：

- 完整运行自己构建的内容
- 读取生产环境日志
- 执行部署并观察发布过程
- 发布版本
- 切换功能开关
- 处理并分流 Bug 工单
- 直接给客户发送邮件沟通

在 Amp 团队，他们针对这些研发流程编写了定制插件，包括处理工单、给用户发邮件、查询“系统是否健康”以及分配功能开关。具体开放哪些工具和操作权限，取决于项目的实际授权。

当 Agent 需要端到端运行测试、安装所需依赖时，Ball 个人更偏好使用远端机器而不是本地环境。在本地开发时，多个 Agent 同时跑流程容易遇到端口冲突或运行依赖争抢；而在独立的远端环境中，更容易让每个 Agent 自行安装并运行完成任务所需的工具，减少本地开发机上的资源打架。

#### 让它批量试验，再等你来判断

在传统的对话方式中，人往往习惯于来回单步试错：“试试改这个……不对，再试试那个”。Ball 的提醒是：如果总在意从发出请求到它开始回答要等多久，很可能还是把自己绑在每一轮回复上。

更高效的协作是**转向异步**与**让 Agent 自建工具去迭代**：

1. **不单步试错，让 Agent 构建测试工具**：
  面对方案选择时，与其一次次口头尝试，不如让它直接生成批量选项：“生成 20 种不同的变体，并做一个简单的页面让我组合测试”；在排查性能问题时也可以针对原因发问：“给出 4 种导致变慢的假说，然后把这 4 种假说全部验证一遍”。
2. **让 Agent 等待人类，而不是人类等待 Agent**：
  异步协作的核心，是交给 Agent 范围更大、更有野心的任务，让它自行执行直到跑出可以验收的结果，再由人来检查判断，而不是让人守在屏幕前等待每一步的流式输出。
3. **利用定时任务与唤醒机制**：
  定时与唤醒让它能在稍后的指定时机继续工作。例如给 Agent 下达“2 小时后检查日志”、“上线后通知我”、“每天早上 9 点检查一次”等指令，让它在指定时机自行触发并跟进结果。

#### 同一个任务，反馈由谁传递？

流程示意：对比同一任务中，人介入的位置与 Agent 能取得的反馈。

##### 人逐轮传递
01 · 交代任务

人指定一个优化办法，再请 Agent 改代码。
02 · 怎样尝试

改一版，人运行一次，再把结果贴回对话。
03 · 能看到什么

Agent 只能看到人转发的片段。
04 · 怎样判断

人继续给下一条修改意见。

##### Agent 自己取得反馈
01 · 交代任务

给目标：让编译器与虚拟机尽可能快，以快两倍为目标。
02 · 怎样尝试

让 Agent 提出可能原因，搭工具逐个验证。
03 · 能看到什么

Agent 自己运行程序，读取测试结果，再修改。
04 · 怎样判断

交付前后数据与运行记录，人判断是否支持目标。

性能目标要用运行结果核对；前后使用同一测试任务和条件，才能比较是否更快。

#### 会话留下决策背景，规则还要检验有没有用

Ball 的做法是一个任务留在同一条会话里，较早的对话由工具自动整理成摘要，接着往下做。他觉得这种上下文压缩已经很好用，不再手动计算还剩多少对话容量。他自己的会话有的只有 46 条消息，有的长达 3,714 条。

在 Amp 中，这些会话线程与 Git 提交直接关联；日后团队回顾“当时为什么这么做”时，可以顺着提交追溯当时的讨论和决策背景，减少不必要的重复摸索。

代码库中往往会积累 `AGENTS.md` 项目说明、技能、脚本和文档，但 Agent 是否真的用到了这些内容？Ball 建议做盲测对照：新启动若干个 Agent（例如 5 个），让它们在不知道要验证哪条结论的前提下做同一类任务，一组提供这些规则文件，另一组不提供，以此观察规则是否切实起到了作用。

#### 人工审查集中在出错影响大的地方

对于“Agent 是否会产生大量垃圾代码，导致代码库变得无法维护”的担忧，Ball 表达了个人观点：六个月前或许如此，但现在他不再确信 Agent 必然会增加垃圾代码；而且即使存在冗余，他也不确信结果就一定无法维护。（这是作者对当前实践的判断，原文没有长期维护性数据。）

在代码审查上，他的取舍是：**把逐行代码审查集中在出错波及范围大的地方**——也就是一旦出错，会波及很多模块、核心数据或大量用户的关键部分。

对于普通代码，如果满足以下条件：

- 它能正常运行，并且 Agent 已经完成了端到端测试
- 在架构图层面结构清晰、容易理解
- 一个月后如果需要修改，自己仍然能够改得动

那么它究竟是用闭包还是类、类型定义是否格外整洁、变量名是否符合特定偏好，甚至是否存在局部的代码重复，他都不再花精力逐行纠结。

他的人工审查主要集中在两处：

- **极少数核心骨干文件**：在 Ball 自己的代码库中，这类牵涉全局的核心文件少于 5 个，需要人工重点审慎把关。
- **数据库迁移**：数据持久层的改动往往波及深远，属于典型的高波及范围修改。

人仍要验收运行结果、判断整体结构是否清楚，以及以后能不能修改；减少的是对普通代码局部写法的逐行纠结。影响全局的关键改动，则需要更深入的人工代码审查。

写给人看的文字，他也划了自己的分工：除了排障步骤、事故复盘报告和部分文档这类偏机械记录、读者端感受不太要紧的内容外，不让 Agent 代写给人类看的文字。

Ball 想省下的是逐轮传话、逐行纠结局部写法的精力。他仍然要决定做什么、核对结果是否成立，并审查出错影响大的地方；Agent 则负责把中间的试验与修正连续跑完。

### 目标放开，证据收紧

不锁死实现做法，需要配合可检验的完成标准。Ball 建议团队明确“哪些答复不算证据”；以下是他看重的三类依据，并非每个任务都必须同时提交三种。
走查从开始到结果实际走通视频展示程序真实运行表现数字相同基准下比较改动前后

### 把真实反馈接进来

Amp 团队把测试、生产日志、部署发布、功能开关、工单和客户邮件等流程接成工具，让 Agent 能取得实际反馈、继续调整，减少人逐轮转述。工具接通有助于检验，不能保证它每次都判断正确。

Ball 个人更偏好远端机器：多个 Agent 本地运行时容易争抢依赖或端口；独立环境更方便它们安装并运行所需工具。

### 从逐轮陪跑，转向异步批量
每次只试一步人说“试试这个”，等待回答；失败后再提下一个方案。人一直跟着每轮输出走。交一段完整任务让 Agent 生成 20 种变体供组合测试，或提出 4 种变慢假说并全部验证；跑出结果后等人判断。

定时、唤醒和心跳让后续检查可以继续：例如 2 小时后查日志、上线后通知、每天早上 9 点检查。这里的数字都是指令例子。

### 模型要选，规则也要验证

**把返工时间算进模型成本。** Ball 倾向最新、最强的模型，以减少排错与重试；文中的“10% 出错”是假设例子，不是测试数据。

**文档存在，不等于 Agent 真会用。** 可启动若干个新 Agent（例如 5 个），在不告知预期结论的情况下，让有规则文件和无规则文件的两组做同类任务，比较规则是否实际有用。

### 把人工审查放在影响大的地方

Ball 不再确信 Agent 必然增加难维护的代码；这是他的个人判断，原文没有长期维护性数据。他减少对普通代码局部写法的逐行纠结，仍要判断运行结果、整体结构和后续能否修改。
普通代码的前提端到端测试跑通；架构层面清晰；一个月后自己还改得动。满足这些条件，才放宽对闭包、类、命名或局部重复的纠结。需要深入人工审查影响全局的核心骨干文件与数据库迁移。Ball 自己库中的核心文件少于 5 个，这不是其他项目的数量上限。

**会话留下决策背景：**一个任务留一条会话，较早内容交由工具压缩；在 Amp 中，可顺着 Git 提交追溯讨论和决策。

**面向人的文字自己写：**Ball 只把排障步骤、事故报告和部分机械性文档交给 Agent；这是他的写作分工。
