在 AI Engineer CODE 2026 大会上，SpaceXAI 工程师 Lauren Tan（网名 poteto）亮出了 Grok Bot 团队的一组数字：上个月约 1.1 万个 PR 上线到生产环境，客户端大约每天发一个稳定版，PR 被撤回的比例却不升反降，稳定在约 0.5%，差不多每 200 个才退回 1 个。她本人上个月就上线了约 3,000 个，很多是在她睡觉时合进去的。

PR（pull request）是一次提交给代码库的改动，审过、测过才合进去，像在共享文档里提交一组修订、等人批准；撤回，就是合进去之后发现有问题，又整个退掉。一个月 1.1 万个，平均每个工作日约 500 个，没有人能逐行看完。那这些代码凭什么让人放心？

演讲题目先亮了态度：《All Code Is Slop (Except Mine)》，「所有代码都是垃圾，除了我的」（slop 是这两年骂 AI 批量糊出来的劣质内容的词）。她的回答分两半。第一半：Agent 会照抄代码库里的一切，包括你留下的烂补丁，所以每纠正它一次，就写成一条自动检查，别往 AGENTS.md（写给 Agent 看的项目说明书）里加一句。第二半：让 Agent 自己把应用跑起来，交回录像、截图和状态图，人审这些证据，不再逐行读代码。

Grok Bot 是 SpaceXAI 和 Cursor 一起做的「AI 同事」：每个 Bot 有一台自己的云端电脑，能在各种应用之间替你干活。她举的反面例子，多半出自她以前参与的 **Cursor 编辑器**（一款用 Electron 做的 AI 编辑器）的代码库。

### 信任倒金字塔：越往下，拦一次错越贵

她用一个倒过来的金字塔，安排力气该花在 Agent 环境的哪一层。从上到下五层：

- **代码库：**好的 API 设计、架构、重构，让错误的写法根本写不出来。
- **静态检查：**lint 规则（自动检查代码写法的规则）、类型系统、编译器、各种测试、CI（每次提交后自动跑的那套检查）。
- **验证：**让程序真的跑起来看效果（运行时验证），或者用数学方法检查设计（形式化验证）。
- **文字：**规则、技能、AGENTS.md，留给需要判断力、写不成代码的事。
- **人工审查：**最后由人来看。

![幻灯片：怎样更信任我的 Agent，poteto 金字塔，五层倒金字塔与成本箭头](https://pic.xiaohu.ai/jiedu-media/lauren-tan-agent-code-quality/02-07-trust-layers.webp)

**「我怎样才能更信任我的 Agent？」：**她管这叫「poteto 金字塔」。从上到下依次是代码库（好的 API 设计、架构、重构）、静态分析（lint、类型、编译器、测试、CI）、验证（形式化、运行时）、文字（规则、技能、AGENTS.md）、人工审查。左边的箭头写着「成本」，往下越来越大。

前两层是「确定的」：写好之后每次提交都自动执行，结果不看 Agent 那天的状态。验证层用来抓 bug、检查系统里必须一直成立的规则，也顺带检查 Agent 有没有理解你的意图。文字放在后面，人工审查在最底下。

箭头上的「成本」演讲里没展开，可以理解成每拦住一次错要付的代价：一条 lint 规则写一次，以后每次提交都免费执行；一句写给 Agent 的话，要它每次都读到、读懂、照做；人工审查每一次都要占用人的时间。金字塔上面越宽，越多问题在便宜的地方就被拦下了。

#### 纠正一次，就写成一条检查

由此她给出了全场最具体的一条建议：每次纠正 Agent，先想想能不能把它变成一条确定的检查，别再往规则文件或 AGENTS.md 里加一行。写进代码，结果每次都一样，你也更敢信它。

文字规则还有一个更隐蔽的毛病。她观察到，Agent 会对你随口的一次小纠正反应过度，把它当成以后永远不能破的硬规则。一句话写下去，它可能读漏，也可能在不该管的地方也照搬。

照做照做又犯照做

一条 lint 规则管的范围，就是代码里写明的那几种写法，不会被「理解过头」；违反了，提交当场失败，报错信息还能直接告诉 Agent 该去改哪。

### 代码库是 Agent 最大的输入，烂补丁会被照抄

Agent 按输入产出，而代码库是它最大的一份输入。动手之前，它会先翻代码库，看这个项目「一般怎么写」。于是代码库里的临时绕行、反模式、早该删的旧写法、技术债，在下一个 Agent 眼里都像是项目的既定惯例，会被照抄过去。

她把代码库比作花园。2024 年她上班，要审的是同事写的 3 个 PR；现在这个数更接近 300。每个工程师背后是几百甚至上千个 Agent，代码像连续的水流一样涌进来，像活物一样自己生长。你立下的约束和护栏，是新代码围着它长的混凝土地基。杂草也一样：一处没拔，没等你发现就满园都是。

![幻灯片：每多一份拷贝，下一份拷贝就更可能出现，一株杂草的根在地下蔓延成一片](https://pic.xiaohu.ai/jiedu-media/lauren-tan-agent-code-quality/04-45-copied-workaround.webp)

**「每多一份拷贝，下一份拷贝就更可能出现」：**左下角标着「一处临时绕行」，三个箭头都写着「复制」，地下的根连成一片，右边标着「惯例」。

所以在她看来，工程师的活越来越像园丁：把代码库收拾得尽量干净，让 Agent 每次照抄到的都是好东西。

#### 一个定时器补丁，38 天长成 183 个

她举了一个 Cursor 编辑器代码库里的真实例子。这款编辑器是在 VS Code 的基础上改出来的，界面又大量用了 React，两种写法是拧着的：VS Code 习惯一步步下命令改界面（先把这个删掉，再把那个画上），React 习惯描述界面应该长什么样，由框架去改。两边对不上的地方，Agent 最爱用的速效药是定时器：`setTimeout`、`requestAnimationFrame`、`requestIdleCallback`，意思都是「先别动，过一会儿再做」，把冲突糊过去。

![幻灯片：速效药有害，9 月 9 日一个定时器修闪烁，10 月 3 日被复制进共享模块，10 月 17 日变成 183 个定时器](https://pic.xiaohu.ai/jiedu-media/lauren-tan-agent-code-quality/07-58-timers.webp)

**「速效药有害」：**9 月 9 日，一个 Agent 为了修一处界面闪烁写下 `setTimeout(() => release(id), 0)`，上面附一句注释「过一会儿再释放，以防它又回来」；它不改根因的理由是「那会是一个更大的改动」。10 月 3 日，这个写法被复制进一个共享模块；10 月 17 日，代码里已经有 183 个定时器。

最糟的是，Agent 还写了很多注释，解释这个速效药为什么合理。下一个 Agent 读到这些注释，就更确定这是项目认可的做法。很快定时器到处都是，应用的性能明显变差。

定时器多了为什么会卡？JavaScript 里大量定时器被飞快地创建又销毁，会留下成堆的内存垃圾，触发大规模的垃圾回收（程序停下手里的事，清理不再用的内存）。清理的那段时间里，界面画不出新的一帧，用户看到的就是卡顿、掉帧。

#### 注释是负债：Grok Bot 禁掉了 99% 的注释

到了 Grok Bot，他们吸取教训，定下规矩：禁掉 99% 的注释。她给了三个理由：注释很容易过时；人其实懒得读那一堆注释；注释还给了 Agent 一个逃生口，写一段理由，就能心安理得地不去做那件难但对的事。

![幻灯片：注释是负债，7 月 31 日 65,824 条，今天 1,227 条](https://pic.xiaohu.ai/jiedu-media/lauren-tan-agent-code-quality/08-56-comments.webp)

**「注释是负债」：**代码库里的注释，7 月 31 日有 65,824 条，演讲时只剩 1,227 条，砍掉约 98%。「禁掉 99%」是她说的规矩，这里是实际剩下的条数。图下注明她的插件 pstack 里有对应的 /no-comments 技能。

更根本的问题是，注释没法强制执行。「我留句话，告诉下一个 Agent 别这么做」，听上去是好意，可没人能保证它被照做，也就谈不上信任。所以在 Grok Bot 和 Dune 里，他们改用 lint 规则，并且把报错信息写得很有用：直接告诉 Agent 去修根本问题，别再绕着打补丁。

### Dune：让错误的写法根本写不出来

Dune 是他们给 Grok Bot 写的客户端框架，可以把它想成桌面应用版的 Next.js（一个流行的网页开发框架）。她说它技术上并不新奇，值钱的是里面的约束和 lint 规则，装着他们做桌面应用踩过的坑。

#### 需要分寸才能用好的东西，干脆禁掉

其中一条教训：需要拿捏分寸才能用好的东西，最后多半会变成 slop。典型是 React 的 `useEffect`：官方文档说它用来让界面组件和外部系统保持同步，不和外部系统打交道多半用不着它；现实里它常被滥用，有人开玩笑说用好它得有个博士学位，Agent 更用不好。他们干脆在产品代码里禁用它，只许 Dune 自己的少数接口内部使用，这类问题从此整类消失。

#### 目录本身就是给 Agent 的说明

另一个反模式同样出自 Cursor 编辑器的代码库。Electron 应用（用网页技术做的桌面软件，Cursor 编辑器和 Grok Bot 都是）有两种进程：**主进程**在后台管窗口、文件、通知、更新；**渲染进程**负责画界面、响应打字和点击。好比后厨和前厅，前厅服务员跑去后厨炖汤，客人就没人招呼了。Agent 常把主进程的代码直接引进渲染进程，耗时的活挤到画界面的地方跑，界面就卡。

在 Grok Bot 和所有 Dune 应用里，顶层就两个目录，直接叫 `electron-renderer` 和 `electron-main`，两边互相引用会被依赖分析工具和 lint 规则拦下。规则不难写，审代码时又少一件要操心的事。

![幻灯片：目录结构本身就是一种上下文，Dune 的 electron-renderer 和 electron-main 目录，以及 tibo.dog 的文件名](https://pic.xiaohu.ai/jiedu-media/lauren-tan-agent-code-quality/06-30-electron-directories.webp)

**「目录结构本身就是一种上下文」：**上半是 Dune。左边 electron-renderer/ 放界面这边的 features（功能）、client（客户端）、primitives（基础组件）；右边 electron-main/ 放 startup（启动）、notifications（通知）、update（更新）。两边之间打了叉，写着「连类型都不许互相引用」，只能共用中间 shared/ 里的共享类型。下半是她的业余项目 tibo.dog：文件名 `src/sim/tick.hot.ts` 本身就在告诉 Agent，这段代码「每一帧都会跑」「不许分配新内存」。

总的原则只有一条：每纠正 Agent 一次，就把它变成一条确定的检查，或者通过更好的 API、更好的架构，让这一整类问题从代码里消失。这样做得够多，审代码时要盯的东西就越来越少；到某一天你会发现，已经没什么可审的了，大部分 PR 可以让 Agent 自己合进去。

### 审代码，变成看 Agent 交来的证据

要审的代码少了，审查本身也变了样。她说团队的代码审查已经缩成了看「验证产物」：录像、截图、图表、形式化验证的结果。验证也是让 Agent 更能自己做主、让人更敢信它的关键一层。

#### 让 Agent 自己把应用跑起来

最基本的是运行时验证：给 Agent 一个自己运行代码的办法，让它用人类开发者也在用的调试工具，比如 Chrome DevTools Protocol（Chrome 开发者工具背后那套遥控接口，能让程序替人点按钮、量性能）。

他们的验证技能里有一张「功能地图」，像网站地图一样，从用户的视角列出应用里所有功能在哪、怎么到达。你说「左侧栏那个东西」，Agent 不用猜，双方有了共同的叫法。技能里还带着他们专门写的命令行工具，Agent 每次都复用同一套工具和驱动程序，省 token，工具本身也能测试。

#### 一段录像，只走过一条路

录像只能证明 Agent 走过的那一条路没问题。最近他们开始试形式化验证，用数学的办法把所有的路都查一遍：

- **TLA+：**把一段流程写成状态模型，让机器把各种事件的先后顺序都试一遍，检查定下的规则是否始终成立。他们用它检查主要的用户流程，比如通知在多台设备、多个平台之间怎么走。
- **Lean：**给一段算法写证明，每一步推理都由机器核对。他们自己写了一个虚拟滚动库（几千条的聊天记录，屏幕上只画看得见的十几条，滚到哪画到哪），用 Lean 检查它不会出现闪烁、抖动。

录像走一条路，模型检查把每种先后顺序都走一遍

示意图：例子是我们编的，演讲只说他们用 TLA+ 检查跨设备的通知流程。

要一直成立的规则：**一条消息在任何一台设备上读过，同步完成后，其他设备都不该再显示它未读。**

**1**手机收到消息**2**电脑收到消息**3**在手机上读掉**4**「已读」同步到电脑

**1***→***2***→***3***→***4**电脑：已读 ✓平时手动测、录一段视频，走的多半就是这条最顺的路。
**2***→***1***→***3***→***4**电脑：已读 ✓
**1***→***3***→***2***→***4**电脑：已读 ✓
**1***→***3***→***4***→***2**电脑：一直显示未读 ✗「已读」先到了电脑，那时电脑上还没有这条消息；消息后到，被当成了新的未读。

**一段录像**证明了第一条路没问题
**模型检查**四条都走，找出第四条违反规则

![幻灯片：形式化验证，TLA+ 给状态机建模，Lean 给代码写证明](https://pic.xiaohu.ai/jiedu-media/lauren-tan-agent-code-quality/10-58-formal-verification.webp)

**「形式化验证」：**左边两个气泡，TLA+ 是「给状态机建模，检查它的规则都成立」，Lean 是「给代码写证明，核对每一步推理」。右边两张卡：TLA+ 模型用来检查所有状态都被正确处理；Lean 证明用来检查实现里的 bug。图下注明 pstack 里有教 Agent 搭形式化验证的技能。

她说这套方法还在试验，看着很有希望，已经找出了不少 bug，但不是万能药，只是 Agent 环境里又多了一层。另外他们刚开始给界面做「属性测试」，用的是 Antithesis 公司开源的 Bombadil：它会自己在界面上到处探索、乱点乱试，检查你规定的性质有没有被破坏。这个也已经抓到几个界面 bug。

#### 以前太贵的验证，现在便宜了

她引了 Cindy Sridharan 的两条推文。半年前 Cindy 抱怨好几个 AI 生成、带隐蔽 bug 的 PR 被合了进去（见下图），她那时信不过 Agent，缺的正是验证；半年后，Cindy 说她每天 70% 的 token 花在验证上。Lauren 说自己也一样，大部分 token 都花在验证。

![幻灯片：Cindy Sridharan 的推文，好几个 AI 生成、带隐蔽 bug 的 PR 被合并](https://pic.xiaohu.ai/jiedu-media/lauren-tan-agent-code-quality/11-56-verification-tokens.webp)

**Cindy Sridharan 半年前的推文：**「可能只是个例，但就这周，好几个 AI 生成、带隐蔽 bug 的 PR 被合了进去，又花了好几天、做了大量人工核查才修好。」后半句：「算上修 bug 花的力气，所谓的『速度』根本没涨。」

她特别指出，Cindy 流程里用的没有一样是新发明，都是软件工程里早就有的好工具，只是过去难懂、难写、难维护，贵到划不来。Agent 把这笔成本砍了下来，所以她说我们正进入软件测试和验证的黄金时代：以前不值得测的东西，现在可以测得透得多。

这里便宜下来的，是搭验证要花的人力：写模型、写证明、维护测试，现在可以交给 Agent。金字塔的先后顺序不变：能在代码库和静态检查里拦住的错，仍然先在那里拦。

### 回报：1.1 万个 PR，撤回约 0.5%

这么多投入换来了什么？Grok Bot 团队上个月往生产环境上线了约 1.1 万个 PR，客户端的发版也快了，大约每天出一个稳定版。核心团队交付得更多，偶尔顺手来帮一把的人也多了，他们不一定了解来龙去脉，也能贡献代码。10 月有约 227 人至少提交过一个 PR。

交付这么快，会不会乱成一团、堆出一堆垃圾？她给的数字是：被撤回的 PR 占比反而降了，稳定在约 0.5%，也就是大约每 200 个合进去的 PR 里有 1 个又被退掉。

她觉得更有意思的是性能。她说和刚上线时比，客户端整体稳住了，好几项还更快：启动、打字、开新聊天、切换聊天。幻灯片对比的是 5 月和现在，也老实列出了变差的几项，最明显的是启动时加载的 JS 和 CSS 多了 285%、拖动调整窗口慢了 130%、空闲时 CPU 占用翻了一倍。她也提醒，Grok Bot 现在还是 Electron 应用，速度有天花板，但已经比很多 Agent 应用的界面快。

### 先把内圈修好，再自动化外圈

她的劝告是：在搭「软件工厂」、把能自动化的都自动化之前，每次纠正 Agent，先从改进代码库做起。先写一条 lint 规则，挡住新出现的反模式，再把旧的清掉；然后把验证做扎实。这些本来就是自动化的前提。

理由很直白：如果你写代码的内圈（Agent 写、验证、发现问题、再改）产出的是垃圾，把这个圈自动化，只会产出更多垃圾，还得往里砸越来越多的 token，那可不便宜。

![幻灯片：别把一个坏循环自动化，低信任循环与高信任循环对比](https://pic.xiaohu.ai/jiedu-media/lauren-tan-agent-code-quality/16-00-inner-loop.webp)

**「别把一个坏循环自动化」：**左边是低信任：Agent 写出垃圾代码，人来验证，发现问题，再回到 Agent，「大多数人卡在这里」。右边是走完 poteto 金字塔之后的高信任：Agent 写出好代码，Agent 自己验证，发现问题。底部：「先改进你的循环，再自动化！」

地基打好之后，外圈就容易搭了。外圈她用的是自家的 Grok Bot：它有大量连接器；有定时任务（routines），可以启动 Cursor 云端 Agent；还有「项目」，能调度几百上千个 Agent 一起干活。

她举的例子是发布流程。现在每切出一个新版本，Grok Bot 就自动开一个 Cursor 项目，对整个新版本做模糊测试（fuzz：用大量随机、出人意料的操作去试，专找崩溃和异常）。这个「Cursor 项目」是 Grok Bot 调来干活的一批 Cursor 云端 Agent，和前面反例里的 Cursor 编辑器不是一回事：它们像真用户一样把应用跑起来用，每找到一个 bug 就开一个修复 PR，然后自动合入。

她说代码库已经好到 PR 默认就是好的。

![幻灯片：Grok Bot 作为外循环，一份 Linux 版模糊测试结果报告截图](https://pic.xiaohu.ai/jiedu-media/lauren-tan-agent-code-quality/16-38-release-example.webp)

**「Grok Bot 当你的外圈」：**一个名叫 sandcastle 的 Agent 发在讨论串里的 Linux 版模糊测试报告（部分内容打了码）。它测了稳定版安装包，每个发现都和旧版 0.79.4 对比；合并 2 组重复后共 50 个不同的 bug：新出现的 3 个（0 个高危、2 个中等、1 个低），以前就有的 47 个（1 个高危、9 个中等、37 个低）。两个新的中等 bug 出自哪部分代码，原图打了码；唯一的高危 bug 在 0.79.4 上也有。每个 bug 在串里单开一条回复，新的排前面，下面一共 53 条回复。

她说敢这样做，是因为代码库已经好到 PR 默认就是好的；他们合入的大部分产品代码，已经不需要人深度审查。地基打牢、架构自己长得好，就能把 slop 变成金子：交付又快，质量也不打折扣。

### 演讲没讲到的地方

读完最容易冒出三个问题，演讲只给了部分答案：

- **哪些改动可以自动合，哪些一定要人看？**她只说「大部分产品代码」不再需要深度人工审查，发布后找到的 bug 修复会自动合入。哪几类改动仍然要人看，没有给出清单。
- **写代码和做验证的都是 Agent，谁来查验证本身？**她的回答是人改成审验证产物：录像、截图、状态图。至于验证漏了路径、拿错了对比基准怎么办，演讲没讲。
- **撤回率之外，线上出的问题怎样？**演讲只给了撤回比例和性能数字。发布后的模糊测试报告能看到一点：那一版新出现 3 个 bug，没有高危。别的线上故障数据没有给。

这些数字都是团队自己报的，PR 有大有小，也不能直接换算成生产力。可那条顺序谁都能马上用上：下一次你纠正 Agent，先别往 AGENTS.md 里加那一句，看看它能不能变成一条 lint 规则、一个类型约束，或者一次让错误写法消失的重构。然后回头把代码库里同类的旧写法清掉，因为下一个 Agent 会照着它们学。
