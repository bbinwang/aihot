技术博主 Matt Pocock 与 [Lauren Tan](https://best.xiaohu.ai/article/cursor-agent-engineering/)（网名 Poteto，开源项目 pstack 的作者、现任职于 SpaceX AI／Cursor）进行了一场深度对谈。

Lauren 介绍，自己正在参与 Grok Bot 这款 Agent 应用的工程工作，上个月合入了 2,500 个 PR。（PR 是提交给代码库审查和合并的一组改动）两人核心探讨的是：如何摆脱当 AI 的“人形搬运工”，借助 Agent 与工具链，让代码工作从写出来走到自行验证、合并，并达到她所描述的交付规模？

访谈里，Lauren 描述的工作方式，很少涉及怎样更快地输入提示词。她把大量时间花在另一件事上：找出 Agent 为什么还需要自己介入，再让系统接住这些工作。

[pstack](https://cursor.com/marketplace/cursor/pstack) 是一套技能插件，把她的开发方法整理成 Agent 能使用的技能和工作流。她分享的 PR 数量包含许多代码维护变更，不能等同于数千个新功能。这个数字值得关注的地方，是持续交付不再要求她亲自启动、指导和检查每一项工作。

这恰好戳中了很多 AI 开发者的困境。代码生成变快了，人的一天却仍被“帮它看看”“给它补点背景”“再提醒一次规范”填满。Agent 能替你执行，但整套工作依然围绕你的注意力运转。一旦多开几个任务，等待你回答的问题也跟着增加。

要走出这个局面，需要改变工程经验的存放位置。原本只有你知道的检查方法、设计习惯和项目背景，必须逐渐进入工具、代码库与信息通道。Agent 才能在需要的时候获得它们，而不必每次停下来等你。

### 从人工介入的地方，找出系统缺少的能力

Lauren 最早的尝试并非发生在大规模团队里。离开 Meta 后，她休息了一段时间，又开始做个人项目。用 AI 写代码时，她发现自己花了很多时间微观管理单个 Agent，便开始把自己的工作方法写成技能。她想让 Agent 更像自己那样处理问题，而不仅是生成一段能用的代码。

这里有个容易被忽略的细节：她当时也很难衡量技能到底带来了多大改善。写出工作流文档，与证明 Agent 真能独立把工作做好，是两件事。

后来加入 Cursor，她参与智能体窗口的性能优化。界面为什么卡顿，需要查看性能火焰图，了解时间主要耗在哪些操作上；还要检查内存快照，判断内存使用是否异常，再据此寻找代码问题。最初，这些观察主要由她完成：她看工具，把发现告诉 Agent，Agent 改代码，她再回去检查。

在这条链上，真正稀缺的能力并非输入代码，而是获得结果并解释结果。只要这一步始终需要人，Agent 的下一次行动就始终依赖人。

因此，“哪里又需要我帮忙”可以成为一个具体的工程问题。它可能意味着 Agent 没有观察运行结果的工具；也可能意味着它不知道最新需求，或代码库没有表达清楚哪些做法不可接受。弄清缺的是哪一种能力，才能决定该补什么。继续加一句提示词，有时只会把同一个问题推迟到下一轮。
