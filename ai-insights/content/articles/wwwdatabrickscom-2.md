- 语音正在改变客户与品牌互动的方式。那些从实体店转向网站、再转向应用的人们，如今期望能直接与自己购买商品的公司对话，而同样的转变也正在延伸到供应商、司机和外勤团队。
- 迄今为止，大多数企业 AI 都面向内部。而更大的机会在于企业每天与客户和合作伙伴的对话之中，如今每一次这样的对话都可以被实时捕获、理解并据此采取行动。
- 任何团队都可以构建一个能开口应答的语音 Agent,但只有当 Agent 了解来电者是谁时，价值才会产生。在此基础上，它可以针对每位来电者进行适配、在既定规则范围内运作，并随着每一次通话不断改进。
- 在 Databricks 上，Agent 的“大脑”与您的受治理数据并肩而居。Context 和 ontology 为每一个回答提供事实依据，快速的 AI 决策为每一轮对话量身定制，而每一次通话都为学习闭环提供养分。
- 起步非常简单：选择一个高频的常规来电，衡量 Agent 处理它的表现，并以 DIVA blueprint 作为下一个场景的起点。

### 为什么是语音，为什么是现在

想一想消费类业务中每天都在发生的三个场景：

- 清晨 6 点，一名司机因即将错过送货时间窗口而致电调度中心，希望调整他的月台预约。他正在开车，所以无法使用应用。另外三名司机已经在排队等待，而每一分钟的等待都可能让下一笔配送面临风险。
- 正午时分，一家得来速餐厅有四辆车排队，只有一名员工戴着耳机接单，同时还要收款和递送餐品。顾客只能通过说话下单，因此队伍的移动速度完全取决于一名员工处理订单的速度。
- 傍晚，一场暴风雨导致航班停飞，滞留的旅客致电酒店要求保留房间并推迟入住。站在登机口、两手都提着行李的情况下，打电话比使用网站更简单快捷。预订团队只有两名员工，却有四十通电话涌入。

在上述每一个场景中，语音都是客户联系企业最快或唯一的途径。既然语音最终能最有效地满足客户和业务需求，为什么它往往不可用，或如今又执行得不尽如人意？

多年来，答案一直是语音很难做好。但这已不再是事实。如今，合成语音听起来已经很自然，通话内容可以在来电者尚未挂断时就被转化为文本并据此采取行动，而且今天的语音 Agent 已经能够跟上人类对话中互相应答通常所需的约 [200 毫秒](https://www.pnas.org/doi/10.1073/pnas.0903616106) 的节奏。

尚未跟上的，是大多数企业对此的思考方式。企业 AI 投资在很大程度上一直面向内部，即服务于员工的助手，而更大的机会在于企业每天与客户和合作伙伴之间的对话。美国最大的快餐厅品牌之一正在朝这个方向迈进：其语音 Agent 让顾客只需开口说话，即可将商品加入购物车、修改订单并完成结账。

*语音 Agent 可以创造价值的示例用例。*

从调整月台预约的司机到暴风雨后保留房间的旅客，每一次这样的通话，依赖的都远不止是理解语音。要真正有用，Agent 需要拥有与最优秀的员工相同的 Context:来电者是谁、针对该来电者已有哪些事项正在进行，以及它被允许就此采取哪些行动。

### 缺失的一环是了解你的客户

大多数语音 Agent 试点只能证明 Agent 能够进行对话，而能证明它可以被托付给真实客户的却少得多。Context 正是弥合这一差距的关键。有了 Context,Agent 就能针对每位来电者进行适配，在您设定的关于它能看到什么、能说什么的规则范围内运作，并随着每一次通话不断改进。没有 Context,即便是最自然的语音，也只能给出千篇一律的泛泛回答。

不妨从一通电话说起。一位忠实客户来电咨询订单延迟。agent 已经知道对方是谁、订了什么、包裹现在在哪里。它道歉，提供授权范围内的忠诚度积分补偿，并安排补发。如果客户仍然不满，agent 能当场察觉，并在瞬间之内决定将通话转接给下一位可用的人工坐席。对方接起时已掌握完整上下文，因此客户既无需排队等待，也无需重复陈述。同样的模式也适用于患者改约就诊时间，或订阅用户在看到一笔陌生扣款后无法登录的情形。在每一种情况下，agent 都在客户离开 app 或网站、急需答案的时刻介入，并在通话结束后将其送回原来的旅程。

在实时通话中汇集这些上下文才是真正的挑战。这些数据散布在众多系统中，agent 需要瞬间之内获取，而且全程必须处于治理之下。这正是 Databricks 发挥作用的地方。

### voice agent 背后的大脑:Databricks 之上的上下文、本体与治理
![](https://www.databricks.com/sites/default/files/inline-images/diva-brain-behind-the-voice-agent-4x.png?v=1793196853)

一个 voice agent 由两部分组成。第一部分是**对话层**,负责通话本身:传输音频、将语音转为文本、朗读回复。专业的合作伙伴产品在这方面表现出色。在我们的原型中,[LiveKit](https://livekit.com/) 承载通话,[Deepgram](https://deepgram.com/) 负责 speech-to-text 并提供默认语音,[ElevenLabs](https://elevenlabs.io/) 则增加了富有表现力的语音能力。[Twilio](https://www.twilio.com/en-us) 这类电话服务商则可以接入普通电话线路。

第二部分是**大脑**,由 Databricks 提供。在通话的每一轮中,它都会查询来电者的上下文,应用你的业务规则,并选择下一步动作——是回答问题、提出优惠,还是将通话转给人工。它还会记录每一项决策,供你的团队事后审查。对话层塑造 agent 的声音,而大脑决定它的回答是否正确。

大脑建立在三大基础之上,而它们本就共存于 Databricks 之中。

- **Context** 是 agent 在当下所需的数据:属于来电者的客户、订单、产品和政策数据。
- **Ontology** 是这些数据之间的关联方式。它承载你的业务赖以运转的定义与关系——例如什么条件让某人成为 loyalty member、一笔订单属于哪家门店、哪项政策适用于哪个产品——从而让 agent 能像你的员工一样对你的业务进行推理。
- **Governance** 决定谁能看到什么。在 Databricks 上,AI agent 在你的[企业数据目录](https://www.databricks.com/product/unity-catalog)中遵循的访问规则,与你的员工已经遵循的完全相同。

对 Databricks 客户而言,无需另建新平台。agent 就在你的数据所在之处运行,并通过经审批的只读查询,连接到你已有的系统,例如订单、loyalty 和 CRM 系统。

#### 支柱 1:让每个回答都根植于你的业务

在与客户交互的过程中,agent 会利用你的 context 和 ontology 查询该客户的订单、你的政策以及你的产品信息,因此每个回答都反映你的业务,而非来自互联网的泛泛之谈。agent 只能看到属于来电者的记录,并且通过核验你的系统来确认对方身份,而不是轻信其口头陈述。你的业务决定 agent 可以提供哪些优惠、能给予多少额度补偿,以及在什么节点由人工接手。

如果 agent 在你的数据中找不到答案,它会如实告知来电者,并将通话转给人工,而不是凭猜测作答。它给出的每一个回答都可以追溯至其来源记录。敏感话题——例如医疗、财务或安全类问题——会按设计转给人工,且 agent 在构建上绝不提供医疗建议。只有对话本身经由语音合作伙伴处理,客户数据始终留在你的受治理平台上。

#### 支柱 2:用快速 AI 决策为每一次对话量身定制

语音 Agent 需要两种思考方式。有些决策必须在极短时间内完成,比如判断一位遇到装卸码头问题的司机或一位愤怒的来电者是否应立即转接人工。另一些则需要仔细推理,比如为延误订单找出正确的解决方案。研究人员称之为[快思考与慢思考](https://us.macmillan.com/books/9780374533557/thinkingfastandslow/),即 System 1 和 System 2,如今 AI 正在以同样的方式构建。大语言模型(System 2)负责仔细推理,而一类新兴的快速决策模型(System 1),例如来自 [TypeSafe AI](https://typesafe.ai/blog/introducing-system-one-models-and-jev) 的 Jev,负责处理快速判断。Databricks 通过 [ai_decide](https://www.databricks.com/blog/introducing-aidecide-make-fast-decisions-your-governed-data) 将 System 1 决策能力带入您的受治理数据中,让 Agent 既能快速做出判断,又能展示其置信度。

在语音 Agent 中,两者在对话的每一轮中协同工作。

- 忠诚会员或回头客可以获得其完整历史记录以及符合资格的优惠,由您最强大的模型提供支持;而常规问题则能以更低的成本获得快速、准确的回答。
- 愤怒的来电者会被转接给人工客服,同时附带订单或预订信息、之前的投诉记录以及已提供的优惠。
- 中途切换语言的来电者会听到 Agent 随之切换语言。
- 看到一笔不认识的扣费且无法登录的订阅用户,会通过与您的记录比对完成身份验证,并直接进入账户恢复流程,而不是在通用队列中等待。
- 来电取消服务的订阅用户,会在优惠仍能改变其主意的时机,听到他们真正符合资格的挽留优惠。
- 询问某个症状是否严重的患者,会被连同完整通话记录转接给护士。
- 报告装卸码头事故的司机,会在造成运货损失之前被立即升级处理。

这让您可以在真正影响客户体验的环节使用您最强大的模型,而其他场景则使用更快、成本更低的模型。

#### 支柱 3:用每一次通话构建学习闭环

上述每一项决策都会被记录下来。在电话层面处理好来电者同意和录音告知之后,每次通话都可以在一个受治理的位置完整留存:说了什么、查询了什么、由哪个模型回答,以及每项决策背后的原因。您的团队可以使用与治理其他数据相同的策略,控制谁能访问这些记录以及保留多久。该 Agent 继承了 Databricks 平台的安全与合规计划,包括 [HIPAA](https://www.databricks.com/trust/compliance/hipaa) 和 [SOC 2 Type II](https://www.databricks.com/trust/compliance/soc) 选项,详见 [Databricks Trust Center](https://www.databricks.com/trust)。语音合作伙伴拥有各自的认证,需要在部署过程中作为一部分加以审查。

正是这份记录让 Agent 得以持续改进。每次通话都可以自动进行质量评分,联络中心和客户体验负责人可以用自然语言就通话提出问题,例如上周二退款请求为何激增。这些洞察随后可以反馈到更好的提示和模型中,进一步提升语音 Agent 的效能。

### 在 Databricks 上开始使用语音 Agent

入门并不需要庞大的项目。构建模块如今已经就绪,而在 GitHub 上开源的 [Databricks Intelligent Voice Agents (DIVA) blueprint](https://github.com/datasciencemonkey/diva) 为您的团队提供了一个可运行的起点。语音由此成为您现有系统之上的一个新渠道。

语音 Agent 的作用是承接那些填满队列的常规来电,例如订单状态、补货和重新预订,让您的员工能够专注于需要人工参与的对话:愤怒的客户、复杂的请求,或者只是更愿意与人交谈的来电者。当员工接起电话时,完整的历史记录已显示在其屏幕上;而一旦出现问题,通话会连同完整文字记录转接给人工。

这正是客户服务的发展方向。**Gartner** 预测，到 2029 年，agentic AI 将在无人干预的情况下[自主解决 80% 的常见客户服务问题](https://www.gartner.com/en/newsroom/press-releases/2025-03-05-gartner-predicts-agentic-ai-will-autonomously-resolve-80-percent-of-common-customer-service-issues-without-human-intervention-by-20290),从而带来 **30% 的运营成本削减**。

Databricks 行业工程师建议从为期 90 天的试点开始，覆盖一个渠道、一个团队，以及业务量最大的常规来电，例如订单状态查询、司机签到或供应商确认。在试点开始之前，记录当前的单次通话成本、处理时长和客户满意度，并追踪来电者是否再次光顾并复购，以便最终对比结果。一旦结果经得起检验，你就可以将同样的治理化配置推广到更多地点和更多类型的通话。

**下次领导层会议需要讨论的三个问题**

1. 我们最常处理哪些客户和合作伙伴的对话？其中哪些现在是 Agent 就能准确应答的？
2. 如果明天由一个语音 Agent 代表我们接听，它知道自己正在与谁交谈吗？它会遵守与员工相同的规则吗？
3. 我们能否追踪 Agent 在通话中做出的每一个决策，并证明其处于治理之下？
