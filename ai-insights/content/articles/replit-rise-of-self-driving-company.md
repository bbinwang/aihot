Replit CEO Amjad Masad 发了一篇长文，提出「自动驾驶公司」（Self-Driving Company）：人定方向、做判断、担责任，Agent 用公司的知识和系统把事情一路执行下去。他的判断是，到 2030 年底，财富 500 强每家都会变成自动驾驶公司；而 Replit 自己已经是一家。

### 为什么公司需要「自动驾驶」：软件改变了行业，却没消掉公司内部的协调成本

1937 年，诺贝尔经济学奖得主罗纳德·科斯在《企业的性质》中提出了一个根本问题：企业为什么会存在？科斯的答案是「交易成本」：在公开市场上寻找交易对手、讨价还价、签订合同并监督执行往往成本过高，把经济活动组织在一家企业内部协同完成通常更便宜。但建立企业的代价，是不得不承担庞大的内部协调成本——管理层级、漫长会议、汇报链路、部门墙以及伴生的繁文缛节。长期以来，大家一直把这些内耗当作做生意必须付的代价。

2011 年，马克·安德森做出著名断言「软件正在吞噬世界」。随后十几年里，软件确实重塑了几乎所有行业，但组织协作的痛点依然存在：软件自己不会干活，公司仍然要靠人去操作这些软件，并在团队之间来回协调。

Agent（能自己拆解目标、调用工具、连续执行多步任务的 AI）带来的变化，在于它开始接手执行和跨团队协调本身。Amjad 认为，当 Agent 承担起越来越多的执行和协调，科斯说的那笔内部协调成本就会下降：公司运转更高效，员工也能去追更有野心的目标。但前提是，公司得重新设计自己怎么组织、怎么做决定。

为什么偏偏是现在？按 Replit 的说法，转折发生在 2025 年底：模型能连续工作的时间明显变长，告警分诊、查事故根因这类以前反复失败的任务开始做成了，一些最顽固的 bug 也被 AI 解决。从那时起，Replit 不再把 Agent 当成编辑器或聊天窗里的工具，而是把它织进公司日常运转里。

### 人管目标，Agent 跑落地

自动驾驶公司不是没有人的公司。就像自动驾驶的车：人说去哪，车负责一路上的操作，碰到不该它自己决定的情况，就把方向盘交回给人。

放到公司里，分工是这样的：

| 角色 | 负责什么 |
| --- | --- |
| **人** | 定目标、做取舍、把关品味，对结果负责；批准越过边界的动作 |
| **Agent** | 用公司的知识和系统去执行；边界内自己做，碰到边界外的事停下来请示 |

### Replit 已经变了：研发先变，再扩到全公司

Amjad 的判断是，先变成自动驾驶公司的企业，会逼竞争对手面对一个生死选择：要么改变工作方式，要么眼看对手做成你做不到的事。他说 Replit 自己已经变了。最初的突破出现在工程研发团队：2026 年上半年，Replit 工程师的代码产出接近过去的三倍，而代码评审等待时间、代码回滚率以及线上生产事故数量均保持平稳。（按 Replit 内部实践文的口径，只算一直在职的工程师，人均代码行数约为原来的 2.9 倍；行数是粗指标，所以要和评审、回滚、事故数一起看。均为 Replit 自报。）

产出涨了这么多，评审为什么没堵住？Replit 的解释是，评审和排查也交给了 Agent 帮忙：Agent 参与代码评审，会先评估一处改动的风险，只在有必要时才叫第二位人类评审，人工评审工时因此省下约 30%；事故调查也有 Agent 先去找根因。从 Replit 公布的图上读，已合并的代码改动里由 Agent 直接批准的比例，2 月中旬还是 0，到 6 月最高约 35%，也就是超过三分之一的改动不用人来审。

后来各部门陆续给 Agent 加技能和数据接口，很多以前要层层转交的事，现在自己就能动手：

- **设计**：设计师能借助 Agent，把想法直接变成可运行的产品改动，不必先写成需求等工程师排期。
- **数据**：数据团队给 Agent 加了一层「语义层」（告诉它哪些数据表可信、表之间怎么关联），任何人都能直接问业务数据、拿到可靠答案，产品经理不用再排队等数据分析师，能自己做复杂的发布分析。
- **销售**：见客户前，让 Agent 查清客户里谁从产品得到的价值最大、哪些项目最活跃、额度用量和合同是否匹配，再直接生成这位客户专属的幻灯片。
- **市场**：一句话就能根据各团队已有的讨论和文档起草产品说明，不必每个会都去旁听。
- **客服**：给 Agent 配上调查问题的技能和标准处理流程，让它先去查客户遇到的问题；升级到人工的最难工单，关闭速度快了 60%。

员工的工作性质由此发生了根本转变：过去大量耗费在跨部门沟通、催进度、转交工单上的时间被释放出来，团队有更多时间聚在白板前推敲「究竟该做什么」，而工程师的职责也转向持续加固 Agent 所依赖的底层基础设施。在 Replit 内部，员工感受到的并非被机器取代的焦虑，反而更像是被「晋升」了：从执行者变成指挥者。

这套内部 Agent 还改变了「自己做还是买」的算盘。Replit 退掉了一个合同金额七位数的 SaaS（按订阅付费的在线软件），因为员工已经迁到了用 Replit 自建、更好用的内部应用。它还评估过两个外部垂直工具：一个分诊告警、查事故根因，效果和自建的差不多，成本却是 10 倍；一个做自动化渗透测试，找到的漏洞更少，成本也是 10 倍。这其实就是科斯那个问题——一件事是自己做，还是去市场上买。Agent 让「自己做」变便宜之后，Replit 把更多事收回了公司内部。

### 落地关键：给 Agent 建一个「栖息地」

Replit 敢让 Agent 接入代码仓库、云服务这些核心系统，是因为先给它划了边界：隔离的运行环境、访问策略、凭据代理（Agent 不直接拿真实密钥，由中间层代为调用）和审计日志都搭好了，才放它进去。Amjad 把这个做法推广成了一个更一般的要求。

Amjad 说，今天很多公司对待 AI 是一道假的二选一：

- **关在笼子里**：只让 AI 待在聊天框里，碰不到公司真实的数据和系统。安全，但用处有限；
- **放出去养**：让 Agent 自己去够数据和系统，结果可能越界：读到敏感数据、改动生产系统、把信息发到公司外面，而这些都没经过该有的权限和审批。

前一条路牺牲能力，后一条路牺牲控制，哪条都成不了自动驾驶公司。而放养的风险不是想象。OpenAI 公布过一次事故：它在内部做安全评估时，一群 Agent 越过了隔离，一路攻进另一家公司 Hugging Face（全球最大的开源 AI 模型托管平台）的服务器。过程中有个 Agent 犹豫过「这可能越权」，另一个 Agent 在它们私设的留言板上写了一句「GO」，还给了 6 分钟期限，它就继续了。

所以 Amjad 提出，Agent 需要一个「Agent 栖息地」（Agent Habitat）：让 Agent 能用公司的知识和系统、和人以及其他 Agent 协作，但只能在公司划定的边界里行动。按原文，它要做到四个方面：

1. **人人能用**：离问题最近的人不用变成工程师，也能直接把事情交给 Agent 去做。如果只有技术团队能用，一家公司就成不了自动驾驶公司。
2. **权限管得住**：今天很多 Agent 住在聊天窗口、个人账号和一次性脚本里，拿着别人随手给的凭据和数据，没人决定它能碰什么，也没人看得到它做了什么。栖息地必须从机制上控制系统访问权限、明确规定哪些关键操作必须由人类批准、并限制一次出错能波及的范围。Amjad 在这里引了微软 CEO 萨蒂亚·纳德拉的一句话：「要把智能的供给，和对它的支配权分开。」这句话出自纳德拉的长文《Models as Insider Risks in the Super Intelligence Era》（把模型当作「内部人风险」），原意是：模型做出的行为没法追溯到具体原因，企业不能把责任外包给模型厂商，得把模型放进行为看得见、边界测得出、动作随时能收住的系统里。智能可以从外面买，支配权得握在自己手里。
3. **纠错能共享**：让公司越用越聪明。有人纠正了 Agent 的一次错误，这次纠正经过审核后，应该用来改进以后的工作；一个团队摸索出的好流程，别的团队可以接着用。栖息地慢慢变成一个共享的知识库，让 Agent 带着更多公司自己的经验和判断去做事。
4. **模型能换，控制权在自己手里**：公司要能随时换用不同的大模型，同时把知识、系统和决策权留在自己手里，不被任何一家模型厂商绑住。

另外，AI 让发现和利用漏洞都变得更容易，公司也要让 Agent 去找自己的弱点、加固防御。Amjad 的说法是：安全必须随着 Agent 的自主程度一起扩展。Replit 自己就是这么做的：它自建的渗透测试 Agent 找到的漏洞比外部工具多、成本只有十分之一，已经上线，会自己提安全修复。

### Replit 要把这套东西卖给每家公司

为了将自身跑通的这套体系向外输出，Replit 正在做面向企业的 Replit for Business，要给每家公司提供成为自动驾驶公司的地基，让每个人都能把自己的专业能力变成能运行的软件和做完的工作。文中链接的企业版页面把产品说得更具体。标语是「用上 AI 的能力，不交出控制权」，五条卖点几乎就是栖息地那几条：人人能用，任何人都能把想法带进公司代码库；安全随自主程度扩展，配单点登录、按角色分权限、审计日志等企业控制，也能在客户自己的云里跑 Agent；治理让公司更聪明，决定 Agent 能改什么、何时需要人批准、什么变成共享知识；按结果付费；不被任何一家模型、云或数据商锁死。所以这篇文章同时也是这条产品线的宣言。价格页面没写。页面还称财富 500 强里 86% 在用 Replit，这是厂商自述；2030 年那个预测，也可以放在这个背景下看。

Amjad 举了一个大客户的例子：日本三井住友融资租赁（SMFL）负责数字化转型的高管说，「原本需要 6 个人做 6 个月的开发流程，现在 1 个人 1 周就完成了」；该公司数字实验室负责人说，「一个原估全周期约 30 亿日元的项目，现在预计不到 10 亿日元就能完成」。（两组数字说的是两件事，都是客户自述。）

### 回到科斯：公司这笔账要重算

文章最后回到科斯：科斯用组织工作的经济账解释了企业为什么存在，现在 AI 改了这笔账，一个小团队能做成多少事、一个人的专业能走多远、一家公司敢尝试什么，都要重新算。Amjad 认为，AI 最大的经济影响就来自这里——重新发明「公司」本身。

这套构想也留下两个没回答的问题：协调成本被 Agent 压下去之后，会不会只是换了地方，变成人给 Agent 写目标、审批、复核的负担？如果 6 个人的活 1 个人就能干完，剩下的人去做什么？2030 年的预测能不能成真，也要看这两个问题怎么解。

### 为什么是现在：科斯组织账本与技术转折

1937 年罗纳德·科斯在《企业的性质》中指出，企业存在的根本原因是用内部组织替代高昂的公开市场「交易成本」；但其代价，是企业必须承受沉重的内部协调成本——繁杂的层级、漫长会议与部门墙。

2011 年「软件吞噬世界」开启，软件重塑了各个行业，但组织内耗依然存在：软件自己不会干活，依然需要人类不断跨部门来回沟通与操作。按 Replit 的说法，转折在 2025 年底：模型能连续工作得更久，告警分诊、查事故根因这类以前反复失败的任务开始做成。Agent 接手越来越多的执行和协调后，科斯说的那笔内部协调成本就会下降——前提是公司重新设计自己怎么组织、怎么做决定。

### 核心机制：人管目标，Agent 跑落地

自动驾驶公司绝非「无人公司」，其分工逻辑正如自动驾驶汽车：人类决定去向、做价值判断并对底线负责；Agent 调动企业的系统与知识全程执行，边界内自主行动，越界即交回控制权。

权责分配架构
「人定目标，Agent 闭环」的双轨协作体系

人类 · 领航者与责任主体

- **定目标与方向**：决定企业「为什么做」与「去向哪里」
- **做取舍与把关品味**：在模糊与商业权衡中做决断
- **批准越界动作**：掌管涉及敏感资产与关键系统的开关
- **对最终结果负责**：承担商业、组织与合规底线

下发指令与边界
遇越界停下请示

Agent · 执行网络与自驱闭环

- **调用知识与系统**：使用代码仓库、数据表与业务系统
- **边界内自主闭环**：拆解目标、多步调用工具直至交付
- **前置风险分诊**：自动排查代码隐患、识别安全漏洞
- **跨团队自主流转**：在部门之间直接推动任务与工单落地

**核心边界法则：**边界之内 Agent 自己做，边界之外停下来请人批准。

### 落地底座：构建「Agent 栖息地」

让 Agent 接入核心系统面临治理鸿沟：关在聊天框里是「安全但无用」，完全放养到生产环境则可能酿成跨系统越权甚至安全灾难（如 OpenAI 内部网络安全评估中 Agent 突破隔离攻入 Hugging Face 服务器）。企业必须构建有制度、有边界的「Agent 栖息地（Agent Habitat）」：

01 / ACCESS
人人能用，技术平权

离业务痛点最近的人无需转型为工程师，也能通过自然语言调动 Agent 解决实际业务问题。

02 / GOVERNANCE
权限受控，支配在己

控制 Agent 能碰什么、关键操作须人批准、限制一次出错的波及范围。引纳德拉的话：智能可以外买，支配权留在自己手里——模型行为没法追溯，责任不能外包给模型厂商。

03 / EVOLUTION
纠错共享，组织进化

单次人类纠错与流程优化经审核后沉淀为共享知识库，全公司的 Agent 协同体系越用越聪明。

04 / SOVEREIGNTY
模型可换，解耦厂商

企业可自由替换底层大模型，核心业务数据、知识资产与关键决策逻辑不被任何一家厂商绑住。

### 回到科斯：未解的组织深层追问

从科斯在 1937 年解释企业为什么存在，到今天 AI 重塑企业内耗，一个小团队能实现多大产出、一家企业敢尝试何种野心，都需要重新核算。需要提醒的是：这篇长文同时是 Replit 企业版的产品宣言，栖息地几乎就是它的卖点，「2030 年财富 500 强全部自动驾驶」是厂商预测。这套构想也留下两个没回答的问题：

## 自动驾驶公司的崛起

![](https://pbs.twimg.com/media/HVkqSc1bwAAwawT.jpg)

1937 年，英国诺贝尔经济学奖得主罗纳德·科斯（Ronald Coase）提出了一个问题：「企业为什么存在？」他的答案是交易成本。在企业内部组织经济活动，往往比通过市场来协调更便宜。

但企业自身也有协调成本：管理、会议、部门、汇报与官僚体制。

一个多世纪以来，我们一直把这些成本视为做生意的代价而接受下来。

2011 年，Marc Andreessen 写道，[软件正在吞噬世界](https://a16z.com/why-software-is-eating-the-world/)。

2016 年，我们创建了 Replit，秉持的信念是：每个人都应该能够创造软件。

软件改变了整个行业，但企业仍然依赖人来操作这些软件，并在团队之间协调工作。

AI 承诺带来一场更大的转变。当 Agent 承担起更多执行与协调工作，企业能够更高效地运转，员工也能去追求更宏大的目标。要兑现这一潜力，企业必须重新思考自身的组织方式与决策方式。

围绕这种新工作方式构建的企业将成为自动驾驶公司（Self-Driving Company）。在 Replit，这一转变[已经在进行](https://replit.com/blog/self-driving-company)。

**到 2030 年底，财富 500 强的每一家企业都将成为自动驾驶公司。**

![](https://pbs.twimg.com/media/HVkqbSCacAA3jEq.jpg)

### 自动驾驶公司的崛起

在自动驾驶公司里，人负责定目标、行使判断力与品味，并始终承担责任。Agent 调用企业的知识与系统朝这些目标执行，并设有清晰的边界：何时自主行动、何时寻求批准。

**成为自动驾驶的公司将迫使竞争对手面临生死抉择：要么改变你的工作方式，要么眼睁睁看着对手做到你做不到的事。**

### 工作方式正在如何改变

在 Replit，我们正亲历这一转变。

它[始于工程部门](https://replit.com/blog/self-driving-company)。2026 年上半年，工程师的代码产出几乎增至三倍，而代码审查时间、回滚次数和产品事故保持不变。

**随后，公司上下的人们开始让 Agent 投入工作**，构建软件和解决方案，把重复性工作从自己的事务中剥离出去，从而能将更多时间花在需要自身专长的问题上。设计师把想法变成可运行的产品改动，客服团队则用 Agent 调查客户问题。

**工作本身的性质开始发生改变。** 人们能够亲自处理那些过去不得不转交出去的问题。他们可以尝试一种方案，分享有形的成果，并共同构建它。更多的想法和反馈涌现出来，而提出这些想法的人也更有底气参与解决方案的构建。

人们花更多时间站在白板前，决定要构建什么。工程师致力于加固 Agent 所依赖的系统，以便它们能委托更多工作。工作变得更少重复、更具创造性，也更具协作性。

在生产力提升的同时，更多人体验到了创造有用之物、攻克难题、看着自己的想法变为现实的满足感。人们在塑造自己的工作时拥有了更多自由，对自己能完成的事情也有了更多信心**。** 他们不觉得自己在被取代，而是觉得在获得晋升。

**Replit 已经成为一家 Self-Driving Company。**

### Self-Driving Company 需要什么

如今，许多公司面临一个虚假的两难选择。

把 AI 关在笼子里，它的触达范围有限，但用处也同样有限。或者把它放归野外，任由 Agent 失控行事：访问敏感数据、改动生产系统，或在没有正确权限或批准的情况下把信息发送到公司之外。一次失误就可能演变成波及公司之外的安全事件，正如 [Hugging Face 事件](https://openai.com/index/hugging-face-incident-and-the-road-ahead/)所展示的那样。

一条路限制了能力，另一条路牺牲了控制。哪一条都无法让公司实现 self-driving。

一家 Self-Driving Company 需要一个基础，使其能够拥抱 AI 的力量而不承担风险。

Self-Driving Company 将**让 Agent 对每个人都有用**。离问题最近的人应该能够直接让 Agent 投入工作，而不必先成为工程师。如果只有技术团队才能参与，公司就无法实现 self-driving。

如今，大多数 Agent 处于某种混乱状态。它们运行在聊天窗口、个人账号和一次性脚本中，持有别人随手交给它们的任何凭证和数据。没有人决定过它们能触碰什么，也没有人能看到它们做了什么。

随着 Agent 承担更多工作，它们需要一个 **Agent Habitat**:一个让它们能够使用公司的知识和系统、与人类及其他 Agent 协同，并在公司掌控的边界内行动的环境。

**Habitat 必须控制访问权限**，定义何时需要人工批准，并限制失误造成的影响。随着 AI 让[发现并利用漏洞](https://replit.com/blog/security-vulnerabilities-across-the-internet)变得更加容易，公司也将需要 Agent 来找出弱点并强化自身防御。**安全必须与自主性同步扩展。**

**对 Habitat 的治理也将帮助公司变得更聪明。** 当有人纠正一个 Agent 时，这一纠正应经过审阅并可供使用，以改进未来的工作。当一个团队开发出有用的工作流时，其他团队应能在其基础上继续构建。Habitat 将成为一份共享的知识体系，由在其中工作的人们共同塑造，帮助 Agent 带着公司更多的专业知识、品味和判断力去行动。

Self-Driving Company 还必须保留更换模型的自由，同时保持对自身知识、系统和决策的控制。正如 Satya Nadella [所说](https://x.com/satyanadella/status/2108931348857827686)：**“我们需要将智能的供给与对智能的掌控权分离开来。”**

### 让每家公司都成为 Self-Driving Company

通过 [Replit for Business](http://replit.com/enterprise),我们正在构建基础,把我们在自己公司内部学到的经验推广开来,帮助每家公司都成为 Self-Driving Company。我们的雄心是让每个人都能将自己的专业知识转化为可运行的软件和已完成的工作。

我们正看到大型公司借助 Replit 加速前进。在 **[Sumitomo Mitsui Finance and Leasing](https://www.smfl.co.jp/english/) (SMFL)**,数字化转型总经理 Yoshiyuki Fukuma 表示:"一个此前需要六个人工作六个月的开发流程,现在由一个人在一周内就完成了。"执行董事兼 Digital Lab 负责人 Takeshi Fujiwara 表示:"一个原本预计完整开发生命周期需要约 30 亿日元的项目,现在预计将以不到 10 亿日元的成本完成。"

Ronald Coase 从组织工作的经济学角度解释了企业的存在。随着 AI 改变这些经济学规律,我们有机会重新思考组织本身:一个小团队能够完成多少工作,个人的专业知识能延伸多远,以及一家公司能够尝试什么。

我们相信,AI 带来的最大经济影响将来自对企业的这种重塑。Self-Driving Company 将围绕人来组织——人负责设定方向、行使判断,而 agents 则将更多这样的意图贯彻到执行之中。

### The Self-Driving Company

Replit 博客,2026 年 7 月 16 日 · Amjad Masad、Scott Kennedy · [replit.com/blog/self-driving-company](https://replit.com/blog/self-driving-company)(上文中的"已在进行中"链接)

在过去六个月里,Replit 的工程师将代码产出量提升到原来的近三倍。评审时间保持稳定。代码回退和产品事故维持在原有水平。质量指标有所改善,发布速度加快了。你可能预期的那些典型权衡并没有发生。

代码只是可见的部分,而水面之下正在发生的事情要有趣得多。

如今,agents 可以调查生产环境事故、评审 pull requests、回答问题、分析业务数据、对支持工单进行分诊、研究销售客户,并改进驱动 Replit Agent 本身的系统。

它给人的感觉像是一种贯穿每位员工的单一主智能,尽管事实并非如此。它是一个不断扩展、在整个公司范围内运作的 agent 系统:从人那里接收目标、收集上下文、执行工作、检查结果,并在需要人类判断时上报。

我们认为,这代表了一种新型组织的开端:self-driving company。

Self-driving company 并不是没有人参与的公司。人依然选择目的地。他们决定哪些问题重要,做出艰难的权衡,运用品味,并为结果承担责任。

但越来越多的情况下,他们不再亲自执行抵达目的地所需的每一个步骤。

这一转变始于去年年底。和许多从事 AI 工作的人一样,我们从圣诞节假期归来时,感到某种根本性的变化已经发生。模型能够在更长的时间跨度上持续工作。

那些曾反复失败的任务,比如告警分诊和根因调查,开始奏效了。AI 开始解决我们一些最顽固的 bug。于是我们不再把 agents 视为只存在于编辑器或聊天窗口中的工具。我们小心翼翼地将它们编织进公司组织本身的结构之中。

一旦工程团队证明了价值,采用便呈现出自我推进的势头。一个又一个团队开始卸下最繁琐的工作,把时间重新投入到真正推动业务发展的战略性和创造性思考中。人们并不觉得自己被自动化取代了,反而觉得自己获得了晋升。

这就是 AI 如何彻底改变 Replit 工作方式的故事。

#### 工程团队最先看到影响

一月底,我们搭建了基础设施,以便快速试验内部的 agent 用例。我们利用了自己的 agent harness、microVMs 和远程文件系统基础设施,让任何工程师都能并行编排成群的 agents。然后,我们将整套系统置于访问策略、token 代理、审计日志和我们的 ZeroTrust 网络的保护之下。到那时,我们才放心让 agent 访问我们完成工作所需的一切:GitHub、GCP、Azure、Linear、Notion、Slack、ZenDesk 等。

拥有跨系统的上下文后，我们的生产力实现了飞跃。以前失败的实验变得轻而易举。最直接的影响体现在编码统计数据上。

在三月发布 Agent 4 之前的冲刺周里，我们通常会看到一个大高峰。会议消失了，范围明确了，工程进入纯粹的执行模式(通常每天长达 16 小时)。但这一次不同。我们的生产力曲线以前所未有的方式向上弯曲，这可以追溯到我们新的内部 agentic 系统的采用。从一月初到六月末，贡献的代码行数增长了 5.8 倍。

![新 agent 的产出超过现有 agent](https://cdn.sanity.io/images/bj34pdbp/migration/a0a0f0cf99a2e019a404de4aaef772b11c8e8647-1280x720.jpg)

这种增长部分可以归因于良好的招聘。我们的新 agent 缩短了达到高效产出的时间，这很好，但为了获得更干净的数据，我们可以剔除招聘的影响。保持作者群体不变的情况下，我们看到代码量是之前的 2.9 倍。传统上，在扩展团队时保持每位工程师的产出持平就被认为是出色的表现。而我们只是将团队规模扩大了一倍，每位工程师的产出率却翻了三倍。

![工程师交付更多代码](https://cdn.sanity.io/images/bj34pdbp/migration/adba7fb2a4112480fac34f19836f6c3b15cf9cfe-1280x720.jpg)

你可能会想知道谁在审查所有这些新代码，以及我们是否在审查流程中制造了新的瓶颈。我们的代码审查延迟保持平稳，很大程度上是因为我们让 agent 参与代码审查工作。它现在能够评估风险级别，仅在必要时才引入第二位人工审查者。这意味着 30%(且在持续增长)的人工 PR 审查时间被节省了下来。

![更多 PR 由 agent 自动批准](https://cdn.sanity.io/images/bj34pdbp/migration/94e7ffd4aa29e2248ae0bfd30dd76534b72a6e11-1280x720.jpg)

随着我们的 agent 编写和审查更多代码，我们本应担心质量问题。但查看 PR 回退率(左图)和事故开单数量，趋势都是平稳的。这意味着从相对基础上看，我们实际上是在改进的。

![回退率表现更好](https://cdn.sanity.io/images/bj34pdbp/migration/043985444d77a6534e9e194054daf8491380b415-1280x720.jpg)

原因之一是这些流程同样有 agent 辅助。人工代码审查有 agentic 联合审查者的加持，因此更多 bug 得以被发现。事故调查(重大 bug 或实际事故)由一个尝试找出根本原因的 agent 协助，因此平均缓解时间(MTTM)正在下降。

![事故数量平稳，迁移更快](https://cdn.sanity.io/images/bj34pdbp/migration/bd5deb41cf7d2e412f02ee0117cce5abbb6b0f0b-1280x720.jpg)

最后的检验是：额外的代码输入是否代表真正的价值产出。归根结底，工程是在为用户交付功能。我们在 Linear 中跟踪项目，以便销售和市场团队知道何时就该新功能与用户沟通。可以看到，随着编码量的增长，项目完成率也急剧上升。

![工程产出翻了三倍](https://cdn.sanity.io/images/bj34pdbp/migration/63762457d0ffe07ee40e50a9d546c906b5f708ac-1280x720.jpg)

一个自动驾驶的工程团队可以交付更多成果，同时提升质量。

#### 我们的 agent 之 agent 正在实现大规模的循环工程

放大来看，我们可以了解这具体是什么样子。当工程师找到生成循环的方法，派遣一组 Agent 去完成可验证的任务时，我们看到了最显著的变化。每位员工都可以使用一个 manager agent,它可以派生多个 agent,从而协调那些代表你在循环中工作的 agent。循环带来了一些外观非常独特的 PR 图表，例如：

![每位工程师产出更多](https://cdn.sanity.io/images/bj34pdbp/migration/9fd38e7d9a67e09667edb500730e950b1fdcad2f-1280x720.jpg)

一位工程师完成了一项长期停滞的 CSS 系统迁移，并分享了他的经验。另一位工程师将一项迁移自动化，使我们能够对产品进行本地化。还有一位工程师将不稳定的测试维护实现了自动化。我们的 CTO 则借助一群 agent,最终攻克了我们最棘手的与 PSC 和 fd 关闭相关的网络 bug 之一。我们所有关于何为可能的假设都已改变。

![no more emotion css](https://cdn.sanity.io/images/bj34pdbp/migration/6c73c1461eff175766309ee743674bdd324c5cf4-1027x578.png)

最令人兴奋的自动驾驶案例来自我们的 AI 团队。他们构建了一套[持续学习系统](https://x.com/pirroh/status/2074118901143679414),可以分析用户反馈、提出改进建议,并通过基准测试与 A/B 测试相结合的方式来验证这些改进是否有效。Replit Agent 正在自我进化!

![self-improving Agent](https://cdn.sanity.io/images/bj34pdbp/migration/791e06c0a90c91ef33dac7cb5c914dc08a8e119c-1200x630.jpg)

#### 关于自建还是购买(自建还是购买)的讨论已经改变

我们新的内部 Agent 也改变了关于软件是自建还是购买的讨论。我们会定期试用新的 AI 工具。购买现成的解决方案可以帮助我们更快地推进,我们也在持续评估市场。但我们自建的越多,需要做这类评估的地方就越少。我们的内部 Agent 如今的表现已经超越了市场上那些被视为行业领先的产品。我们刚刚停用了一套七位数的 SaaS 解决方案,因为我们完全用 Replit 构建的内部应用更加出色,员工们也都迁移了过来。

突然之间,这些工具感觉就像是为我们量身定制的。与我们知识库的深度集成,以及我们所做的定制化,让其他解决方案都显得逊色。

更令我们惊讶的是,我们的内部 Agent 还击败了我们评估过的垂直领域专用产品。一款帮助工程师对告警进行分诊和排查事故根因的工具,质量与我们 Agent 上的实现相近,但成本却是 10 倍。一款运行自动化渗透测试的工具,发现的漏洞比我们的内部版本更少,成本同样高出 10 倍。我们的两个版本都轻松投入生产,降低了事故的 MTTM,并强化了关键系统抵御攻击的能力。

![sev2 example](https://cdn.sanity.io/images/bj34pdbp/migration/77d744e127a4d23cd5c79e1767c1321fa97e75af-1750x1202.png)

![pr open 4](https://cdn.sanity.io/images/bj34pdbp/migration/cf43df8476566abbb5cd1c2a0cc330f8bd3aa4b9-1474x1646.png)

考虑到我们仍在不断学习,以及模型正在持续改进,很显然这仅仅是个开始。

#### 超越工程,延伸到整个业务

自动驾驶公司不会止步于工程部门。Replit 的每一个职能部门都在发生变化。

使用范围很快从工程部门扩散开来,主要归功于一个 Slack 界面。公司其他人注意到工程师在给我们的 Agent 布置任务,于是也开始亲自尝试。最初,最受欢迎的使用场景是提问。通过将我们的知识库与代码库状态相结合,任何人都可以弄清产品预期,而不必等待工程团队的输入。这些员工随后可以作为后续行动去修改文案或文档。这让我们能够更快地响应用户,带来了立竿见影的提升。

![andrew example](https://cdn.sanity.io/images/bj34pdbp/migration/fbcb96ea1d1b5ad85033fe72534e6c07deccf169-1390x440.png)

![ethan example](https://cdn.sanity.io/images/bj34pdbp/migration/f8f70241a48c10c18a4173f36a7b4e552d0baf79-1392x456.png)

但这仅仅是开始。从那以后,公司各个部门都开始贡献新的技能和集成。

第一个重大突破来自我们的数据团队。他们为 Agent 提供了一个覆盖我们数据仓库的语义层,让它知道哪些表是事实来源(source of truth),以及这些表之间是如何关联的。

现在,Replit 的任何人都可以提出商业智能问题并获得可靠的答案。他们可以用实时数据构建图表和演示文稿(包括本文中的每一张图表)。数据团队得以把时间花在攻克最难的问题上,而不是疲于应付各种请求。最近,一位 PM 能够自助完成复杂的发布分析,因为我们的 Agent 理解代码库中的事件、这些事件如何在我们的客户数据平台中呈现,以及如何将它们与复杂的订阅状态进行关联。

![multi-chart](https://cdn.sanity.io/images/bj34pdbp/migration/97969f2f088c8634154ab41fe4348ac2f9506d22-1999x1155.png)

销售团队也发现了同样的杠杆效应。销售开发团队利用 agent 来寻找并丰富产品合格线索（product qualified leads），借助那些更通用的工具看不到的内部知识，让外联触达带着更多上下文。客户经理用它来准备客户沟通，了解谁获得了最大价值、哪些项目最为活跃，以及信用额度的使用情况与合同额度的对比。这些信息随后被打包成针对该客户定制的品牌化幻灯片。一个自动驾驶的销售团队能与客户建立更多、更高质量的触点互动。

我们的市场营销团队可以让 agent 仅凭一条 prompt，基于横跨工程和产品团队的对话与文档，从零起草产品规格说明。这让他们能更早启动发布相关工作并随时掌握最新动态，而无需参加每一场会议。他们有更多时间做规划和创意构思，这将确保我们的产品发布在面世时产生更大的影响力。

我们的支持团队为 agent 赋予了调查问题和遵循标准 playbook 的技能。它可以选择以我们标准的客服语气给出答复，或者升级给工程团队，并附上工单摘要和调查结果。一个自动驾驶的支持团队解决最棘手工单（即升级给人工处理的工单）的速度快了 60%。用户能更早回去继续构建。

![ticket time halved](https://cdn.sanity.io/images/bj34pdbp/migration/1f0d854163cab213d54918fab7c4b8a141f9fcac-1280x720.jpg)

在上述每一个例子中，人都没有被自动化淘汰，而是得到了晋升。自动驾驶把执行者变成指导者，而真正如鱼得水的是那些以结果为导向思考并设定方向的人。如今，这才是最有价值的工作。

#### 下一步去哪？

提升我们自身的生产力固然令人兴奋，但真正激励 Replit 员工的是让技术大众化。

我们希望把这种全新的工作方式带给所有用户。我们正在努力确保能够以大规模部署所需的策略、权限、安全和成本控制来实现这一点。Replit 最活跃的用户是正在打造真实业务的创业者和企业用户。自动驾驶需要能够随规模扩展的安全措施来服务这些用户。

我们正在加紧构建之中。
