### 一、最重要的概念：从知识库到工作流

文章提出一个很重要的区分：

* Ontology（本体）： 告诉 AI 企业的数据和业务概念是什么意思。

* Skill（技能）： 告诉 AI 一项具体工作应该怎么做。

举个例子：

你告诉 AI：

> 帮我生成上个月的经营分析报告。

普通 AI 可能会查询数据、分析数字，然后写一份报告。

但拥有 Skill 的 Agent 会：

* 确认上个月的数据是否已经完整。

* 查询相关业务指标。

* 按照既定规则检查异常。

* 对异常数据进一步拆解。

* 搜索相关邮件，寻找异常原因。

* 按照管理层要求的格式生成报告。

* 必要时提交人工审核。

区别在于：前者是完成一次任务，后者是掌握了一套可以重复执行的工作方法。

### 二、什么时候应该创建 Skill？

Databricks 总结了五个判断标准：

| 特征     | 典型场景        |
| ------ | ----------- |
| 经常重复   | 每周项目进度报告    |
| 有固定步骤  | 查询、比较、分析、汇总 |
| 输出格式固定 | 管理层要求固定模板   |
| 存在判断规则 | 什么情况属于异常    |
| 总要人工修改 | 每次都要补充相同内容  |

只要你发现自己反复向 AI 解释同一套操作流程，就应该考虑将它封装成 Skill。

### 三、Skill 应该如何设计？

这是文章最有实践价值的部分。

Databricks 建议，在创建 Skill 之前，先把工作流程拆解清楚。

Skill 工作流设计的七个要素

* 触发条件

    用户说什么话，或者出现什么情况时，应该启用这个 Skill？

* 数据和工具

    需要读取哪些数据库、文件、Agent、Gmail 或 Google Drive？

* 执行顺序

    先做什么、后做什么，有没有依赖关系？

* 深入调查机制

    发现异常后，是否需要继续拆解，直到找到合理解释？

* 质量检查

    每次执行都必须验证哪些指标、条件和内容？

* 交付标准

    输出什么文件？采用什么格式？需要多长？交付到哪里？

* 人工干预点

    哪些步骤可以自动完成，哪些必须等待人工确认？

特别值得注意的是：Databricks 并不是让用户自己编写复杂的 Agent 程序。

它推荐采用对话式创建：

* 用自然语言描述工作流程。

* 让 Genie One 反过来采访你，补齐细节。

* Genie One 根据已有业务知识生成 Skill。

* 用户检查并修正 Skill。

这实际上是把 Skill 创建变成了一种工作流程访谈。

### 四、不要把所有工作塞进一个 Skill

文章强调一个架构原则：

小技能、单一职责、组合执行。

例如，一个完整的月度经营报告，可以拆成：

月度经营报告 Skill

负责组织整个工作流程

数据分析 Skill

提取、计算指标

异常调查 Skill

识别、追踪原因

邮件检索 Skill

寻找业务背景

报告生成 Skill

按模板输出

最终经营报告

统一交付

还有一个很有意思的设计：

可以单独创建一个团队通用的「领导层报告格式 Skill」。

其他 Skill 在执行时引用它。

以后只需要修改一次格式规则，其他 Skill 就能复用更新后的标准，而不用逐个修改。

这与软件工程中的模块化、函数复用和公共组件非常相似。

### 五、如何保证 Skill 不会越用越偏？

文章提出了一套测试机制，值得认真借鉴。

1\. Golden Reference（金标准样例）

当 Agent 生成的报告达到预期后，把它保存为标准参考样例。

以后每次修改 Skill，都拿新结果和这个样例比较。

2\. 对话式修正

例如发现报告存在两个问题：

* 数据尚未完整，就提前生成了上个月的报告。

* 把销售额太小的产品波动也列为重大异常。

直接告诉 Agent：

* 只允许分析已经完整结算的月份。

* 销售额低于 5 万美元的项目不列入重大异常。

Agent 更新 Skill，再重新执行。

3\. 必须开启全新对话重新测试

这是很重要的一点。

不能只在当前对话中测试，因为当前对话可能残留了大量上下文。

必须新开一个对话，使用普通自然语言提出任务，确认 Agent 能否自动识别并调用正确的 Skill。

这才是真正验证 Skill 是否独立有效。

### 六、Skill 的企业级管理

Databricks 不仅考虑了个人使用，还考虑了组织级管理。

| 能力            | 作用              |
| ------------- | --------------- |
| Unity Gateway | 集中发布和管理 Skills  |
| Unity Catalog | 权限控制、标签和审计      |
| 团队共享          | 让其他员工直接使用       |
| 编辑权限          | 指定人员共同维护        |
| Clone         | 复制 Skill，创建个人版本 |
| 定时任务          | 按计划自动执行         |

还有一个值得关注的细节：

Skill 可以按照 Agent Skills 开放格式保存，主要文件是 `SKILL.md`，旁边还可以放置模板、参考样例等文件。

其结构类似：

```text
monthly-trading-brief/
├── SKILL.md
├── templates/
│   └── trading-report.md
└── references/
    └── golden-example.md
```

也就是说，它不只是某个平台里的一个隐藏配置，而是可以审阅、修改、维护的文本资产。

更进一步，发布到 Unity Gateway 后，还能供支持 MCP 的其他 Agent 使用，包括编码 Agent。

### 七、定时执行：从被动响应到主动工作

Skill 创建成功后，可以设置定时任务。

例如：

```text
每月第一个工作日：

1. 执行月度经营报告 Skill
2. 检查数据完整性
3. 分析异常
4. 生成报告
5. 发送到指定会话和邮箱
```

如果 Skill 本身设置了人工审核环节，还可以专门规定无人响应时，定时任务应该如何处理。

这一点非常关键：

Skill 不仅是一个被动等待用户调用的工具，还能成为自动化工作流的执行单元。

### 八、这篇文章真正值得关注的架构思想

我认为它最有价值的不是 Genie One 这个产品，而是它体现出的 Agent 架构演进方向。

传统 Agent 和 Skill 化 Agent 的区别：

| 维度   | 普通 Agent | Skill 化 Agent |
| ---- | -------- | ------------- |
| 工作方法 | 临时理解用户指令 | 复用固定工作流程      |
| 操作步骤 | 每次重新规划   | 有明确执行步骤       |
| 质量标准 | 依赖提示词    | 固化检查规则        |
| 输出格式 | 每次可能不同   | 有标准模板         |
| 能力复用 | 依赖对话上下文  | 独立 Skill      |
| 维护方式 | 修改提示词    | 更新技能文件        |
| 团队协作 | 复制提示词    | 发布和共享技能       |

这里还有三个值得提炼的技术思想：

* 知识与方法分离。 业务知识告诉 Agent 世界是什么样的，Skill 告诉 Agent 如何完成工作。

* 工作流程与执行模型分离。 同一个 Skill 可以由不同 Agent 执行。

* 能力与记忆分离。 不应该依赖某次对话记住工作方法，而应该将方法沉淀成可复用资产。

### 九、结合你的 Agent 项目管理体系，应该怎么应用？

你之前研究过 TRAE Personal Agent，也尝试过 OpenClaw、GitHub 交接文档以及 Claude Code 的项目管理方式。

我认为这篇文章恰好提供了一个值得借鉴的方向：把项目管理经验做成 Skills，而不是不断增加 Agent 的系统提示词。

可以设计成下面这个结构：

### 项目管理 Agent 架构

Personal Agent

统一入口、任务识别、工作调度

项目跟踪 Skill

读取 GitHub、检查进度、识别延期

交接管理 Skill

生成交接文档、恢复任务上下文

任务拆解 Skill

分解任务、依赖关系、验收标准

风险检查 Skill

识别阻塞、异常、资源不足

项目周报 Skill

汇总进展、变更、风险和下一步计划

统一项目状态与知识库

GitHub / Markdown / 项目文档 / 任务记录

例如，你使用 Claude Code 开发一个项目：

* Claude Code 负责实际编码。

* 交接管理 Skill 负责记录当前进度、已完成工作、未解决问题。

* 项目跟踪 Skill 定期检查 GitHub 更新。

* 风险检查 Skill 识别长期没有进展的任务。

* Personal Agent 汇总所有项目状态。

这里最重要的是：Agent 不必一直盯着某个对话，也不必依赖开发者每次手动写一份交接文档。

当然，定时调度、后台执行和状态持久化仍需要相应的运行平台支持，单独一个 `SKILL.md` 并不能自动实现这些能力。

对你目前的本地 LLM + vLLM + Hermes + Claude Code 体系而言，这套思想尤其值得借鉴。模型负责推理，Skill 负责固化流程，Agent 负责调度，外部系统负责持久化和执行。
