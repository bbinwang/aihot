#### 请求、中断与错乱指针：两项内存漏洞的成因与后果

若将 PHP 解释器处理网络访问的过程比作一个流水线工位，其内部运行机制便更容易理解。

在使用常驻 PHP 进程的网站中，需要 PHP 处理的网页或表单请求，会被 Web 服务器交给一个 PHP 工作进程（Worker）。Worker 会在为该请求分配的独立堆内存（即“工作台”）上放置零部件：解析提交的数据、构建内部变量索引。脚本处理完毕后，清理程序将工作台清空，常驻待命的 Worker 则接着处理下一个到来的网络请求。

本次披露的两项漏洞，分别利用了工作台上数据刚刚拼装一半、以及旧请求工作台刚被释放时的异常中断。

##### CVE-2026-109618：内存限制中断与未完全初始化的数据误用

根据 [PHP 官方安全通告](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w) 与 [CERT-EU 的技术通报](https://cert.europa.eu/publications/security-advisories/2026-018/)，该漏洞的 CVSS 评分达到 9.2。PHP 内部设置了单次请求的内存配额限制（`memory_limit`），用于防范资源耗尽。当特制请求促使内存分配触及配额红线时，底层机制会直接中断当前的解析执行。

根据 CERT-EU 的分析，该漏洞的根因在于：请求被内存耗尽异常强行打断时，某些内部数据结构尚未完全初始化；而随后触发的请求清理逻辑却误将这部分未完成初始化的数据当作有效对象进行处理与释放，进而破坏了内存状态。

##### CVE-2026-109619：旧请求释放后的悬垂状态复用

根据 [第二项官方漏洞通报](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp) 与 CERT-EU 说明，CVE-2026-109619 的根因源于跨请求的残留状态。

当一个请求发生致命错误被迫终止后，该请求占用的工作台内存会被释放。但在受影响版本中，引擎内部的部分全局状态依然保留了指向该内存区域的引用。后续由同一个 Worker 进程处理的新请求在尚未重置该状态前，便可能误用这些悬垂指针，导致访问已经失效或被新数据占用的内存。

##### 内存错误引发的后果

这些内存错误的后果主要包括两类：

1. **敏感内存泄露（Memory Disclosure）**：当失效或残留的内存指针被引擎误当作合法数据输出（例如反映在响应头或 Cookie 中）时，攻击者无需取得执行权限，便可能直接读取到进程内存片段。这些数据可能包含其他请求或服务器进程驻留的敏感信息，如会话凭证、API 密钥或密码。
2. **远程代码执行（RCE）**：程序不只用内存存放用户内容，还依靠其中的对象引用等内部数据决定接下来处理哪个对象、采取什么操作。若攻击者精心构造请求数据破坏了内存结构，让可控数据被误当成有效的内部结构，后续操作就会走错；通过复杂的利用链，攻击者可进一步控制执行流程，诱导解释器执行注入的恶意逻辑。攻击者获得的是 PHP 或 Web 服务进程已有的权限；影响范围也取决于该运行身份的权限与隔离。

#### mod_php 与 PHP-FPM：运行架构对利用路径的影响

PHP 官方与 [CERT-EU 通报](https://cert.europa.eu/publications/security-advisories/2026-018/) 指出，传统的 Apache `mod_php` 是风险最高的部署模式，而现代广泛采用的 `PHP-FPM` 则展现出不同的利用条件。

两者差异的核心在于 Worker 进程在异常后是否存活并继续承接后续请求：

- 在 **Apache mod_php** 架构下，PHP 作为 Apache 子进程内部模块运行。官方通报指出，在默认配置下，未经身份验证的请求可在任何应用代码执行前触发启动阶段的内存错误并演示远程代码执行。在该模式下，即使启动解析发生异常中断，请求注销流程仍会执行，存活的子进程可能继续复用受损状态。但这属于特定演示路径，并不意味着任意易受攻击的 mod_php 都会被单个请求必然接管。
- 在 **PHP-FPM** 架构下，独立进程池管理 Worker。若在请求启动早期发生致命错误，FPM 的机制会使当前 Worker 进程直接退出，阻断了部分基于启动期状态残留的利用路径。然而，如果请求通过了启动阶段，在业务执行阶段（如应用内部特定的数据反序列化或错误处理逻辑）触发内存中断，Worker 仍可能继续存活并处理下一个请求，研究人员同样证实了 PHP-FPM 下应用执行阶段的远程代码执行路径。

#### 五阶段全球协同与长期安全路径

面对跨越整个互联网生态的基础软件漏洞，[OpenAI 在公告中](https://openai.com/zh-Hans-CN/index/coordinated-disclosure-of-critical-vulnerabilities/) 表示本次 PHP 漏洞只是其已发现并正在着手修复的多个重大安全隐患之一；该机构预期未来由 AI 辅助发现的漏洞将大幅增加，因此需要一套能够重复执行、随能力提升而扩大覆盖的协同响应机制，并据此提出了“五阶段响应”流程，以反映从一份代码修改到全球网站实际获得防护的完整链条：

1. **验证并修复上游漏洞**：由维护者与研究团队确认问题成因，并测试防御方案。这不仅需要验证补丁本身的有效性，还要进行对抗性测试以排查变体和潜在绕过方式。
2. **为关键防护方留出准备时间**：由维护者依据各组织的防护职责、采取行动所需时间以及处理敏感信息的能力决定受邀对象。分发方需将补丁适配至旧版本，托管商需测试缓解方案，安全厂商需验证 Web 应用防火墙（WAF）的拦截规则。参与方获得的信息视需求而定，范围从包含失陷指标的网络日志到更敏感的可运行验证程序；由于共享细节可能反向泄露漏洞线索，扩大覆盖范围与防范泄密风险之间需要审慎权衡。
3. **联合政府机构保护关键系统**：协调各国网络安全机构，协助将防御指导传达至关键基础设施和公共部门。
4. **推动下游产品准备就绪**：随着补丁趋于稳定，扩大至更多下游厂商与托管平台，准备可直接部署的更新包以弥补覆盖缺口。
5. **发布公开指导并支持实施**：正式公开漏洞信息与补丁，并持续指导运维人员进行升级验证和应急处理。

在这一链条中，各环节之所以需要时间，是因为仓促推送未充分验证的补丁可能破坏广泛的业务兼容性。若在此期间发生利用在野传播、信息意外泄露、公开补丁暴露缺陷或修复推进受阻导致风险上升，协调团队便需要重新评估并调整披露时间表。

从长远来看，[OpenAI 公告中](https://openai.com/zh-Hans-CN/index/coordinated-disclosure-of-critical-vulnerabilities/) 提出了四项基础安全演进方向：一是在开发源头采用更安全的默认配置并规避高风险模式；二是将关键组件迁移至内存安全语言，以从根本上消除常见类别的内存安全错误；三是通过形式化验证，在明确假设下以数学证明关键组件满足指定的安全属性；四是建立更严格的沙箱隔离机制，使处理不可信文件或媒体的软件受限运行，即便处理程序被攻破，也能限制其造成的损害。AI 可以在辅助代码理解、生成迁移草稿与编写测试用例中提供支持，但依然需要工程测试与专家审查来确保业务行为一致。此外，公告还就极端场景征询意见：对于政府或其他运维方拥有或获授权管理的系统，如果已失去管理员访问权限，是否应在特定条件与保障措施下利用漏洞进行紧急修补。这仍是需要讨论授权与安全边界的设想。

与此同时，[PHP 基金会强调](https://thephp.foundation/blog/2026/10/21/todays-php-security-release-and-how-were-strengthening-php-security/)，虽然 AI 工具大幅提升了漏洞报告的产出速度，但团队还处理了百余份无效、重复或无法复现的报告；报告筛选、补丁的架构权衡以及兼容性评审依然依靠经验丰富的核心维护者。随着报告数量增加，开源项目在人工审查与工程维护上的资源瓶颈愈发突出，持续的资助与人力投入依然是维持基础软件安全的基石。

#### 从官方补丁到站点安全：版本支持与缓解措施的局限

当官方发布安全补丁后，还要经过下游打包、托管商部署，最后确认真正对外服务的 PHP 已经更新。Hacker News 用户 [spenvo 描述过等待镜像的经历](https://news.ycombinator.com/item?id=50182051)：即使新版本标签已经出现，所需架构的官方容器镜像也可能尚未构建完成。这个当时的个人经历，具体说明了“上游已发布”和“我的部署能用上”之间的时差。

托管商的维护也会产生不同影响。[IDC Frontier 的 Zenlogic 公告](https://www.idcf.jp/rentalserver/maintenance/2026/20261021-2/)计划在日本时间10月21日22时至22日18时升级 PHP、安装补丁。作业期间会停止 Apache，因此客户网站与 Roundcube 网页邮箱无法访问，邮件软件收发和 FTP 不受这次维护影响。[GMO Pepabo 旗下 Lolipop 的维护页](https://lolipop.jp/info/news/8237/)也列出了传统托管产品的客户站点、用户专用页面、FTP、旧网页邮箱等暂停项目；其其他产品的可用功能则分别说明。

[XServer 的公告](https://www.xserver.ne.jp/)展示了另一种情况：暂停自身官网、管理后台等功能，同时保持客户托管服务器运行并推进修补。10月22日日本时间9:30的进展称，管理功能已部分恢复；此前6:45的进展称，PHP 8.2—8.5 的目标服务器已完成补丁应用，旧版本另行处理。因此，看到“服务商维护”，还要继续看它停的是管理入口，还是客户实际使用的服务。

控制权分散也会拉长恢复时间。维基媒体基金会说明，Toolforge、Cloud VPS 内部分服务由志愿开发者管理，使用者能够选择 PHP 版本；基金会需要联系相应服务所有者协同修补，这些服务可能恢复得更慢。

##### 1. 活跃版本与遗留环境的差异

PHP 官方为当前处于受支持生命周期的四个分支发布了正式安全版本：**8.2.35、8.3.36、8.4.27 与 8.5.12**。

对于已结束生命周期（EOL）的旧版本，官方不再提供常规安全维护。根据 [路透社引述 Censys 的测绘数据](https://www.marketscreener.com/news/government-websites-go-dark-as-vulnerabilities-in-programming-language-send-shudder-across-internet-ce785cd9db8df324)，在观察到且能够识别出 PHP 版本的 260 万台主机样本中，约 150 万台在当时运行着没有官方现成修复版本的分支。在技术社区的早期讨论中，[V2EX 讨论区有开发者](https://edge.v2ex.com/t/1250646) 针对大量仍运行在 PHP 7 环境中的老旧业务表达了现实焦虑。虽然官方不再为已停更分支提供常规安全发布，但这并不等同于任何修补都没有：面对此次严重威胁，PHP 安全团队破例为自行编译的用户发布了针对 PHP 7.4、8.0 与 8.1 的最小源码回移（Backport）补丁，部分 Linux 发行版与长期支持（LTS）供应商也会按发行版和支持范围提供维护包；但在缺乏持续运维的遗留系统上，跨大版本升级涉及语法废弃、扩展失效及应用依赖等兼容性负担，难以在短时间内迅速落地。

##### 2. 临时缓解措施的适用条件与局限

对于无法立即完成补丁升级的生产环境，[CERT-EU](https://cert.europa.eu/publications/security-advisories/2026-018/) 与安全建议提出了一些临时配置调整，但这些手段各自具备严格的适用前提，不能替代完整升级：

- **禁用上传进度（`session.upload_progress.enabled = 0`）**：此项设置能够阻断已确认的基于 Session 上传进度的攻击链，但必须在请求解析前生效并重启所有工作进程，且不能覆盖其他变体。
- **取消单请求内存配额（`memory_limit = -1`）**：该设置通过移除单个请求的内存上限，避免执行流程因触发配额而陷入异常中断清理路径，但这是以牺牲可用性保护为代价的。一旦取消单请求配额，异常请求失去了 PHP 单请求配额的约束，运维团队必须在系统层结合容器配额或 cgroup 内存边界来防范整机资源耗尽。这种边界不能随意替换为 `RLIMIT_AS` 或 `RLIMIT_DATA` 限制，因为它们同样会在进程级别触发底层的内存分配失败；并且若物理内存耗尽导致底层系统分配失败，仍可能触及脆弱的异常清理路径。

生产配置的调整需要专业评估与测试；临时措施减少特定路径的暴露，完整修复仍要更新 PHP。

##### 版本比对的四个客观盲区

在实际运维评估中，版本比对结果不能直接等同于系统的安全证明，需要注意以下盲区：

1. **响应头隐藏与未暴露**：生产系统常关闭 `expose_php` 或在网关层剥离版本标头，导致工具因无法提取版本信息而返回 `UNKNOWN`。`UNKNOWN` 代表当前信息不足以判断补丁状态。
2. **发行版源码回移（Backporting）**：Linux 发行版回移补丁时，可能保留原上游版本号，通过完整软件包修订号区分更新。工具只比较上游版本，可能将已修补的包误报为 `VULNERABLE`；应结合供应商公告核对完整修订号。
3. **CLI 命令行与 Web 运行时差异**：在终端直接执行 `php -v` 获取的是当前命令行环境调用的二进制版本，而 Web 服务器（如 Nginx/Apache）后端实际调用的可能由不同 PHP-FPM 进程池或独立容器驱动，两者的具体版本与构建可能并不一致。
4. **`OK` 状态仅代表版本号高于内置阈值**：该状态基于“后续稳定补丁已包含修复”的假设，工具本身并不对漏洞是否可在实际内存中被触发进行独立检验。

运维团队应依据操作系统或发行商的官方安全公告，核对完整软件包版本与承接 Web 流量的实际运行构建。完成升级后，按供应商流程重启相关 PHP-FPM 或 Apache 进程，或重新部署容器镜像，确保服务已切换到修复版本。

软件升级用于堵住漏洞；此前若已被入侵，仍需排查并处理遗留痕迹。修复期间，服务商的全事务 Web 应用防火墙规则有助于缓解已知载荷，但不能替代底层补丁。若无法及时更新且风险较高，可结合自身网络架构，考虑将受影响服务暂时与公网隔离。

### 一个工作台，两种出错时机

**正常流程**
常驻 PHP 工作进程（Worker）为每个请求分配内存“工作台”：解析数据 → 运行脚本 → 清理工作台。同一进程继续接下个请求。

CVE-2026-109618

#### 拼装一半，清理却当作完工

1. 特制请求触及单次内存上限，解析中断。
2. 数据结构尚未初始化完，清理程序却把它当有效对象处理、释放。
3. 内存状态因此被破坏。

CVE-2026-109619

#### 工作台已撤，旧引用却留下

1. 请求因致命错误结束，内存被释放。
2. 全局状态还留着指向旧内存的引用。
3. 同一 Worker 的新请求在重置前误用引用，访问失效或被新数据占用的内存。

**可能泄露信息：**失效指针被误当合法数据输出，可能带出进程中的会话凭证、密钥等。
**可能执行恶意操作：**程序依赖对象引用等内部数据决定后续操作。可控数据若被误认作内部结构，复杂利用链可能改变执行流程。

**权限边界：**攻击者获得的是 PHP 或 Web 服务进程已有的权限；损害取决于配置、运行身份与隔离。

**运行架构影响路径：**mod_php 已演示应用代码执行前的启动阶段远程代码执行。PHP-FPM 的启动早期致命错误会令 Worker 退出，阻断部分路径；但应用执行阶段仍有已证实的利用路径，不能据此免修补。

OpenAI 的五阶段响应依次覆盖**上游验证修复 → 关键防护方准备 → 政府关键系统 → 下游产品就绪 → 公开指导与实施支持**。扩大覆盖前要测试兼容性，也要权衡共享漏洞细节的泄露风险。

2. **发行版软件包／容器镜像**需要适配和构建，源码发布不等于自己的部署已经可用。
3. **托管商与网站部署**服务商暂停管理入口，也不一定暂停客户网站，要看具体维护范围。
4. **切换实际 Web 进程**重启相关进程或重新部署，确认对外流量已由修复构建承接。

**旧版本并非一概无补丁：**PHP 7.4、8.0、8.1 有最小源码回移补丁，部分发行版及长期支持供应商提供维护包，需核对自身支持范围。临时配置调整只能减少特定路径，不能替代完整修补。

### 检查结果，是证据的起点

`php2shell-checker` 对单个 URL 或本地 PHP 二进制做初步**版本分诊**，不测试漏洞能否实际触发。

`VULNERABLE`上游版本低于内置修复阈值。**回移补丁可能保留旧版本号**，需核对完整软件包修订号，避免误报。`OK`版本号通过阈值判断，基于后续补丁包含修复的假设；**不是实际环境的安全证明**。`UNKNOWN`未取得版本等信息，**无法判断**；不能当作安全或脆弱结论。
网络检查默认 HEAD，仅405／501时回退 GET；不跟随重定向或读取正文。本地 `php -v` 也可能不同于实际 Web 运行版本。
**最终核对：**按供应商公告确认完整包版本与实际服务构建。升级堵住漏洞；若此前已被入侵，仍须排查遗留痕迹。WAF 和临时措施不能替代底层补丁。
